## Scope

What a brand's marketing team needs to know whether its ad money works:

1. **Campaigns** with their platform, external ids (Meta campaign and ad ids, `utm_campaign`
   values), products and dates.
2. **Spend**: one figure per campaign per Asia/Dhaka day, entered by hand or imported from
   the Meta Marketing API (Insights) by a daily job, with a token per org.
3. **Attribution** in §11's priority order: an explicit campaign on the order, then the
   click-to-message ad referral, then the `utm_campaign` mapping, then none.
4. **A marketing dashboard** on §11's exact definitions: spend, confirmed orders, delivered
   orders, delivered revenue, CPO, CPDO, delivered ROAS (primary), placed-order ROAS
   (secondary, labelled optimistic) and return rate.
5. **Leads**: source, phone, product and size interest, age band, profession, status, with
   segment reports by product, size, age band and profession.
6. **The Conversions API sender**: a `Purchase` event per delivered order, hashed
   identifiers, `event_id` = order id, sent by a pg-boss job enqueued in the delivering
   transaction.
7. **Hashed custom-audience export**: the re-engagement list's phones as SHA-256 hashes, in
   the format Meta documents for a customer list.

Plus M16's hooks: a promo code takes a campaign id again, behind a composite foreign key to
the brand's own campaigns (M16 follow-up N3, first half).

## Out of scope

- Uploading audiences to Meta through the API (the export is a file the team uploads).
- Google, TikTok or other platforms' spend APIs (manual entry covers them).
- The analytics rollups (`analytics.daily_campaign`, M24) and the leaderboard.
- Ledger postings for spend: paying for ads is already a cash out with the `ad_spend`
  category (M08), see D-253.
- Pixel and CAPI deduplication: the landing page builder (M29) is out of scope (D-290).
- The fraud check: removed by the owner (D-291); nothing here reads a trust score.

## Data model

New schema `marketing`, owned by the new `marketing` module. Every table has `org_id`, RLS
ENABLE and FORCE, composite tenant foreign keys (D-047) and minimal grants.

- `marketing.campaigns`: name, platform (`meta`, `google`, `tiktok`, `other`), product ids,
  start and end dates (Dhaka), status (`active`, `archived`), origin (`manual`,
  `meta_import`).
- `marketing.campaign_refs`: (campaign, kind, value) with kind `meta_campaign`, `meta_ad` or
  `utm_campaign`. Unique per (org, kind, value), so one external id names one campaign and
  attribution is never ambiguous. UTM values are stored lower-cased and trimmed.
- `marketing.ad_spend`: campaign, spend date, amount (poisha, ≥ 0), source (`manual`,
  `meta`). **Unique per (org, campaign, spend date)**: the idempotency check 2 asks for.
- `marketing.leads`: phone (E.164), name, channel, campaign, SKU of interest, size, age band
  (closed list), profession, status (`new`, `contacted`, `converted`, `lost`), notes.
- `marketing.meta_connections`: one per org. Ad account id, pixel (dataset) id, the token
  sealed with AES-256-GCM (never readable, never returned; a 12-hex fingerprint only),
  switches for spend import and CAPI, the name-and-city consent switch, a test event code,
  and the last import's outcome.
- `marketing.capi_events`: one row per (order, event name). Status `queued`, `sent`,
  `failed`, `skipped`; the hashed payload; Meta's response (events received, fbtrace id,
  error code and message). A sent row is final (trigger).
- `promo.codes.campaign_id` gains its composite foreign key.

## Domain functions and what tests them

In `packages/domain/src/marketing` (the `@elysium/domain/marketing` subpath):

- `attribution.ts`: `resolveAttribution(source, index)`. Table tests for every priority
  step, the fall-through when an explicit id names no campaign, and a property that a
  higher-priority match always wins (check 4).
- `metrics.ts`: `campaignMetrics(facts)` and `aggregateFacts(orders, spend, period)`. A
  fixture dataset with hand-computed CPO, CPDO, ROAS, placed ROAS and return rate (check 1);
  null when a denominator is zero; properties for rounding.
- `meta.ts`: normalising phone, name and city as Meta documents; `buildPurchaseEvent()`
  taking an injected hash function; `capiActionSource(channel)`; `capiEventTimeAllowed()`
  (Meta's 7-day rule); `aggregateMetaSpend(rows)` summing ad-level Insights rows per
  campaign per day.
- `leads.ts`: the age-band list and `segmentReport(leads, dimension)`.
- `money`: `decimalToPoisha()` for Meta's numeric spend strings (rounded half away from
  zero, the one rounding rule) and `poishaToMajorNumber()` for CAPI's `value`.

## API, jobs and screens

- `/v1/marketing/campaigns` (list, create, `PATCH :id`, `POST :id/refs`,
  `DELETE :id/refs/:refId`): `Campaign`.
- `/v1/marketing/spend` (list, upsert a day) and `/v1/marketing/spend/campaigns` (the
  picker): `CampaignSpend`, so accounts can enter spend without managing campaigns.
- `POST /v1/marketing/meta/import`: enqueue an import for a date range (`CampaignSpend`).
- `/v1/marketing/meta-connection` (get, put): `Campaign`.
- `GET /v1/marketing/dashboard?from&to`: totals, per-campaign rows, a daily series.
- `/v1/marketing/leads` (list, create, update) and `/v1/marketing/leads/segments`.
- `GET /v1/marketing/capi-events`: the conversion log.
- `GET /v1/crm/reengagement/export?format=meta_audience`: the hashed audience file.
- Jobs: `marketing.schedule_spend_import` (06:00 Dhaka) fanning out
  `marketing.import_meta_spend` per org; `marketing.capi_delivered` per order.
- Orders: `OrdersApi.marketingFacts()` and `conversionFacts()`; a delivery-observer
  registry so the marketing module enqueues CAPI inside the delivering transaction.
- Console `/marketing`: dashboard (lazy-loaded chart), campaigns, spend, leads, segments,
  Meta settings and the conversion log; a hashed-audience button on the lapsed-buyer list.

## Risks

- **PII leaking to Meta or to logs.** Identifiers are normalised and hashed before the
  payload exists; the stored payload is the hashed one; a snapshot test greps the payload for
  every plaintext value (check 3). Tokens are sealed and never logged; URLs carrying a token
  are never logged.
- **A conversion sent twice.** One row per order and event name, a singleton key on an
  exclusive queue, and a sent row that cannot change.
- **An external call inside a transaction.** The import fetches before it opens a
  transaction; CAPI sends between two transactions (read, send, record).
- **A rerun import doubling spend.** The unique (campaign, date) row and an upsert that
  replaces the figure (check 2), run twice against real Postgres.
- **Attribution drift.** One pure function decides, used by the dashboard and nowhere else.

## Status on 2026-10-02

Built on `m18-marketing` (stacked on the fraud removal, `remove-fraud`). The previous run's
domain work and stop-time WIP were restacked as `3a3f7dc`; this session finished the schema
wiring, the module, the jobs, the tests and the console. All four acceptance checks have
tests that pass against real Postgres. The Meta adapters are unverified and off (D-257);
turning them on needs a brand's token, pixel and a test event code. See `docs/progress.md`
for the verify run and the audits.

Audits, same day. The acceptance-auditor's findings were fixed in `560dddb` (tests for
D-257's two switches and the sealed token's org binding, ROAS rounded once, M18 in the plans
index). The ledger-auditor found no critical issue and three warnings, all fixed:

- The spend import could count a Meta campaign's spend twice: when spend typed by hand sat on
  a campaign not mapped to its Meta id, or after a Meta id was moved to another campaign, or
  under two concurrent imports. Two Meta campaigns mapped to one campaign also overwrote each
  other's day. Now Meta campaigns on one campaign are added before rounding once
  (`spendPerCampaign`), an import zeroes imported figures in its range that Meta no longer
  supports, it refuses to run over unmapped hand-typed Meta spend, and a brand's imports take
  turns on the connection row's lock and re-check the ad account (D-252, D-254).
- A conversion Meta accepted was logged as failed if recording it failed. Only the send is
  guarded now; the retry resends the same `event_id`, which Meta de-duplicates (D-256).
- The dashboard bound one parameter per delivered order and would fail above 65,535; the
  order and promo code ids now travel as one array parameter, and the marketing line query
  no longer selects the dispatch cost.

Also from its notes: `poishaToMajorNumber` refuses at 10^15 poisha, where a double stops
carrying every two-decimal amount exactly; the test event code behaviour is written into
D-256.
