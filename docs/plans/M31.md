# M31: One ERP per brand (brand edition)

Wave 3 · Depends on: M30 part 1 · Architecture §30 (new) · Decisions D-470 to D-479

> Planned on 2026-10-05 after the owner's instruction of the same day: "there will be one mother
> ERP that will have separate server instance and separate domain … every other ERP from all
> business will be child ERP. But there will be never mentioned that they are child ERP, they
> will act like they are just only one … no connection between child ERPs … not any single clue
> that all these business ERPs have a mother ERP." Built under continuous build mode (no
> approval pause; the plan is still written first).

## What this is, in plain words

Today one ERP holds all five brands in one database, kept apart by row-level security, and a
super admin can see all five side by side. After M31 every brand gets **its own copy of the
ERP**: its own server processes, its own database, its own web address. Nothing in a brand's
ERP names, lists or hints at another brand or at a head office. The all-brands screens leave
the brand ERP; M32 rebuilds them in the separate mother ERP.

The code stays one codebase. Row-level security and `org_id` stay too: they cost nothing with
one brand per database, they keep the training brand apart, and removing them would be a
large rewrite with no gain.

## Scope

1. **One brand per deployment** (D-470).
   - `ERP_BRAND_SLUG` names the deployment's brand. When it is set, the API and worker refuse to
     start unless the database holds that brand and no other real brand (the training brand is
     allowed). Unset means the old many-brand mode, which tests and local development keep.
   - `pnpm db:seed --brand <slug>` (and `SEED_BRANDS=<slug>`) seeds one brand with its chart of
     accounts, head office and hand-cash wallet. Without it the seed keeps all five, as today.
   - `preview:seed --brand <slug>` seeds and demos one brand.
2. **The all-brands surfaces leave the brand ERP** (D-471). Removed from `apps/server` and
   `apps/console`, and rebuilt in the mother (M32):
   - `GET /v1/analytics/consolidated`, `GET /v1/analytics/leaderboard`,
     `GET /v1/reports/consolidated-wallets`, `GET /v1/reports/consolidated-profit-and-loss`;
   - the console's group dashboard, leaderboard and consolidated accounts screens, their nav
     entries and messages.
   - The `erp_analytics` role stays: the brand's own dashboards use it, and it is what the mother
     reads through (M32).
3. **White label** (D-472). Nothing a brand's staff, customers or website developer can see
   says "Elysium" unless the brand is Elysium, or hints at other brands:
   - names come from the brand's own `org.organizations` row: the TOTP issuer, the SMS code
     text, the console title, PWA manifests, the login fallback, recovery-code file names,
     payslip and document fallbacks;
   - browser-visible identifiers become neutral: the CSRF cookie and header (`erp_csrf`,
     `x-csrf-token`), local storage keys (`erp-theme`, `erp-locale`, …), the till's IndexedDB
     and service-worker cache names (with a one-time migration so a till does not lose its
     offline queue), the intake API's headers (`X-Api-Key`, `X-Api-Timestamp`,
     `X-Api-Signature`, the old names still accepted);
   - copy that only made sense with several brands in one database ("works in another brand",
     "brand switcher", "all brands") is reworded or removed;
   - a test greps the built console, till and portal bundles and the API's public responses for
     `elysium` (case-insensitive) and for the other brands' names, and fails on a hit. Internal
     identifiers that never reach a browser (HMAC labels, Nest symbols, package names) stay:
     changing an HMAC label would invalidate every issued file URL and site key.
4. **Owner sign-in** (D-473). The mother's super admins reach a brand without a password in it:
   - `POST /v1/auth/owner-link` (public, off unless `OWNER_LINK_PUBLIC_KEY` is set) takes a
     short-lived Ed25519-signed assertion `{ iss, aud, sub, email, name, jti, iat, exp }`,
     checks the signature, `aud` = this deployment's `ERP_BRAND_SLUG`, an expiry of at most 120
     seconds and a single-use `jti` (stored in `iam.owner_link_uses`), then signs the person in
     as an owner and redirects to the console.
   - An owner is a `super_admin` with **no password and no membership**: they can only arrive
     by link, they never appear on the Staff screen, and in the audit log and on records they
     show as "Owner" (their real name only to other owners).
   - The session counts as two-step verified (the mother enforced TOTP); the enrolment wall
     treats link sessions as enrolled.
   - Nothing names the mother: the route, its error codes and its docs speak of an "owner
     sign-in link", which is what it is.
5. **Deployment shape** (D-474). `infra/brand/`: one Docker Compose project per brand
   (`erp-<slug>`), each with its own Postgres 17, Valkey, Gotenberg, API, worker and files
   volume, its own `.env`, its own nginx site and certificate, and its own ports on 127.0.0.1.
   `infra/brand/new-brand.sh <slug> <domain>` writes the env file with fresh secrets;
   `deploy.sh` deploys one brand or all. The staff console is served at the brand's admin host
   (default `admin.<brand domain>`; `<brand domain>/admin` redirects there, D-475), so the
   storefront keeps its own `/api` paths.

## Out of scope

- The mother ERP itself (M32).
- Moving existing data between databases: the preview is re-seeded per brand; real brands
  start on M14a's importers or the old-site importer (M36).

## Data model

- `iam.owner_link_uses (jti text primary key, used_at timestamptz)`: global (iam), append-only,
  pruned after a day by the worker.
- No change to tenant tables.

## Risks

- A missed "Elysium" string in a brand's bundle. Mitigated by the bundle scan in `pnpm verify`.
- Renaming the till's IndexedDB could strand a queued offline sale. The till copies the old store
  into the new one on start and deletes the old one only after the copy commits.
- The owner link is a sign-in path. Mitigations: off by default; Ed25519 public key only on the
  brand; audience, expiry and single use enforced; owner sessions are short (2 hours); every use
  audited; rate limited.

## Acceptance checks

1. With `ERP_BRAND_SLUG=oura-lifestyle` and a database holding two real brands, the API refuses
   to start with a message naming the problem.
2. The four cross-brand routes answer 404 and are absent from the route matrix and the OpenAPI
   document; the console has no group, leaderboard or consolidated screen.
3. The bundle scan finds no `elysium` and no other brand's name in a brand build of the console,
   till and portal for a brand other than Elysium.
4. Owner sign-in: a valid link signs in; an expired, replayed, wrong-audience, wrong-key or
   tampered link is refused with the same error; an owner never appears in `GET /v1/users`; the
   audit log shows "Owner" to non-owners.
5. `pnpm verify` green; ledger-auditor on the tenancy and auth diff.
