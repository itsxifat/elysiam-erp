> plan file. This records the plan as executed.

## Scope

Each brand tracks who invested what, declares profit distributions, and pays
withdrawals through maker-checker. An investor can never see another investor's
position or another brand's books.

## Out of scope

- Company loans, which are debt and not equity (M26).
- Reseller payouts (M21, not being built).

## Data model

Schema `investors`, migrations 0058 to 0060.

- `investors`, `investments`: capital contributions, each with its own lock-in.
- `distributions`, `distribution_lines`: one declared profit split per investor.
- `withdrawals`: request, review, approval, payment.
- `documents`: agreements, served only through signed URLs.

## Domain functions and what tests them

In `packages/domain/src/investors`:

- `split.ts`: `splitDistribution`. The parts always sum to the whole, to the
  poisha. Property tested.
- `position.ts`: capital and payable are separate balances, and lock-in is per
  contribution. `assertWithdrawable` refuses what is not yet free.

Posting rules: `investor-capital.ts`, `profit-distribution.ts`,
`investor-payment.ts`, with worked examples in `investors-posting.test.ts`.

## API and screens

- 20 routes under `/v1/investors`: investors, investments, distributions with
  reject, withdrawals with review, pay and reject, documents, statement.
- Two-factor authentication is mandatory for the investor role.
- Console: `/investors` and `/investors/$investorId`.

## The investor portal (added 2026-10-02)

The part M25 left unbuilt: the investor's own pages in `apps/portal`, and the
browser half of check 1. Branch `m25-investor-portal`, from `integration-wave2`.

**What an investor gets, at `/investor`** (Bangla first, English toggle, light
and dark; D-310):

- Sign-in with email and password, then the second factor. The `investor` role
  is behind §6's enrolment wall, so an investor who has not enrolled sees the
  enrolment screen and nothing else until a code verifies. The flow is the
  console's (M02a) against the same Better Auth endpoints; nothing new on the
  server.
- One brand at a time, with a switcher when they hold a stake in more than one
  (D-311). Capital per brand is that brand's position. The session is shared
  with the console, so the portal moves it only when no brand is chosen yet or
  on a click; figures are cached per signed-in user and brand.
- Their position (capital held, under lock-in, withdrawable, profit declared,
  paid and owed), their contributions with each lot's lock-in, the profit
  distributions declared to them, their withdrawals and each one's status, their
  statement, and their documents, each opened through a freshly signed URL.
- No withdrawal form. The `investor` role is read-only in the matrix, so the API
  refuses the request; the page says to ask the brand's accounts team, and
  maker-checker stays on the staff side (D-312).

**What the server needs: no new route.** Every read exists and is scoped to the
caller's own investor row. Distributions come from the statement's declared
entries, because `/v1/investors/distributions` is the org's record and refuses an
`own`-scoped caller. No route, no migration, no api-client change. The ledger
audit added three server rules: nobody signs for a withdrawal paid to themselves
(D-314); an investor's own row omits the brand's staff notes, and the signed
document URL is `no-store` (D-315).

**Check 1's browser half runs against the real stack** (D-313):
`apps/portal/e2e/investor.stack.ts`, started by `pnpm --filter @elysium/portal
e2e:stack`. A stub API would prove only that the page shows what the stub
returns; isolation is the server's property (`own` scope plus RLS), so only the
real API can show it. The run is kept lean: one provision process
(`investor-portal-stack.provision.ts`, which seeds through the real API
in-process), the built API and worker (the API waits for the worker to install
the job queue's schema), and the portal's Vite. No console.

## Decisions

D-019, D-115 to D-121, and D-310 to D-313 for the portal. The ones that change money: a profit divides by agreed
share or by capital held at the period's last day (D-115), a withdrawal touches
the ledger only at `paid` (D-117, a deviation from §15), and investor money
needs three distinct people (D-118).

## Risks that mattered

Five critical findings from the ledger audit, all fixed with tests. The one
worth remembering:

- **A rejected withdrawal permanently reduced the investor's headroom.** The
  pending amount was never released. Rejection now has an explicit route that
  releases it (D-121).

Also: `ApprovalsService` runs executors only on approval, so a rejected request
needs the manual reject route. A rejection hook in the approvals module is a
follow-up.
