## Scope

The pilot brand starts with books and stock its accountant will sign. Six importers,
one opening journal, one reconciliation report, and a demo org for training.

Everything here runs **once per brand, before go-live**, by the implementation team with
the brand's accountant. That shapes two choices the rest of the plan follows from: the
importers are allowed to be slow, and they are not allowed to be approximate.

## Out of scope

- M14b's deployment, observability and the go-live runbook.
- Importing anything that is not needed to open the books: campaigns, payroll history,
  message logs, historical orders as orders. A brand's past SMS is not an opening balance.
- Editing or re-opening an opening balance after it is posted (D-213, amended). A mistake
  found afterwards is corrected through the owning module — a stock count or approved
  adjustment, a wallet closing — so the post names the accountant who agreed the staged
  trial balance.
- A console screen for the importers (D-214). The service holds all the logic, so a
  screen later is a thin edge over it.

## How it is run (D-214, D-215)

`pnpm migration <command> --org <slug>`, which boots `MigrationModule` as an application
context and runs every write as `erp_app` inside the brand's `withOrg` transaction:

- `dry-run --kind <kind> --file <csv>`: the report — rows, skips, every problem by line and
  column, and for a balance file the opening trial balance of this file plus everything
  staged. Writes nothing.
- `commit --kind <kind> --file <csv>`: the whole file or none of it.
- `discard --batch <id>`, `status`, `post --as-of <date> --approved-by "<accountant>"`,
  `reconcile [--out <csv>]`,
  `sign-off --by "<accountant>"`.

Two kinds of importer:

- **Applied on commit**: SKUs (into the catalog) and customers (into the buyer list). They
  are not balances and nothing waits for them.
- **Staged on commit**: opening stock, supplier dues and advances, wallet balances, courier
  COD in transit. The commit records the batch and its parsed rows; nothing reaches stock or
  the ledger. A staged batch can be discarded and replaced. Then `post` writes every staged
  batch in **one transaction**: the `opening_balance` stock movements and the one opening
  journal. After that, balance imports are closed.

Why staged: D-213 opens a brand's books with exactly one journal, and an accountant needs to
see the whole opening trial balance — and fix a wrong file — before anything is posted. A
stock file committed straight into stock could only be corrected with approved adjustments,
after the weighted average had already blended it.

## The six importers

In order of dependency. Columns are named in the dry-run report.

1. **SKUs** (`product, sku, price_taka[, category, size, colour, barcode]`). Rows group into
   products by name; codes are the brand's own (D-219). Existing codes are reported and left
   alone; a product half in the catalog is refused. Written by `CatalogApi.importProducts`.
2. **Customers** (`phone, name[, delivered, returned, cancelled, spent_taka]`). A phone
   already a buyer is skipped, so history is added once (D-218); the buyer's own counters are
   set from the file through `OrdersApi.importBuyers`. No fraud signals (D-291), no dates.
3. **Opening stock** (`sku, location, qty, unit_cost_taka`). One cost per SKU across every
   staged stock batch, cost above zero, and a SKU that already holds stock is refused (D-216).
   Posted as `opening_balance` movements through `InventoryApi.receiveOpening`.
4. **Supplier dues and advances** (`supplier, kind (payable|advance), amount_taka`).
5. **Wallet balances** (`wallet` = the wallet's ledger account code, `amount_taka`).
6. **Courier COD in transit** (`courier, reference, amount_taka`): money a courier collected
   or will collect for parcels sent before go-live, as courier receivable per courier (D-220).

## How the hard checks are kept

**Check 1, the numbers before anything is written.** The dry run of a balance file reports
the opening trial balance of _that file plus every batch already staged_, computed in
`packages/domain/src/migration` with no database: lines by account, the equity plug, and
`balanced`; and `stockValuePoisha = Σ mulQty(unitCost, qty)`. Property tests hold both for any
rows; a database test dry-runs the repo's sample files (`apps/server/migration-sample`).

**Check 2, all-or-nothing.** One `withOrg` transaction per commit and per posting, with the
refusal thrown from inside it. The commit re-reviews the file against current data (M06's
reasoning: valid at 10:02 is not valid at 10:05). Database tests put a bad row at the end of
every importer's file and assert nothing changed, and make the last product, the last buyer
and the opening journal (after its stock movements) fail inside the transaction.

**Check 3, idempotency (D-217).** `migration.batches` holds `(org_id, kind, content_sha256)`
unique among batches that are not discarded. The commit inserts the batch first; a second run
of the same file returns the first batch and writes nothing. SKUs and customers are also
idempotent per row (an existing code or phone is skipped). The opening journal's key is
`opening_balance:<org>:posted` (D-213), and movements carry `opening:<opening>:<sku>:<location>`
dedupe keys.

**Check 4, the journal against the modules.** After posting, the journal's lines are read
back through `LedgerApi.journalLines` and the stock valuation through
`InventoryApi.valuation` — the inventory module's own Σ(WAC × on hand) — and the test asserts
they agree to the poisha and the journal's debits equal its credits. One cost per SKU (D-216)
is what makes the two agree exactly rather than to within a rounding.

**Check 5 (D-222).** `pnpm migration reconcile` puts side by side, for stock, wallets,
supplier payables, supplier advances, courier receivable and the equity plug: what was
imported, what the journal carried, and what the owning module reports as of the opening
date, and writes it as CSV for the accountant. `sign-off` records the accountant's name once,
only when every line agrees; the signature itself is the human's.

## Data model

New schema `migration`, tenant tables, RLS ENABLE and FORCE, composite tenant FKs
(migrations 0081–0083):

- `migration.batches`: `kind`, `content_sha256`, `file_name`, `row_count`, `rows` jsonb (the
  parsed, resolved rows of a staged kind; null for an applied kind), `summary` jsonb (counts and
  totals), `status` (`applied | staged | discarded | posted`), `opening_id`. A trigger allows only
  `staged → discarded | posted` and freezes everything else. INSERT, SELECT and UPDATE of the
  decision columns for `erp_app`; no DELETE.
- `migration.openings`: one per org — `as_of`, `journal_id`, `posted_by`, `posted_at`, and the
  sign-off (`signed_off_by`, `signed_off_at`, `sign_off_note`), which may be set once. No DELETE.

Opening stock becomes `inventory.stock_movements`, the balances become journal lines, buyers
become `sales.customers` — each written by the module that owns it, through its API.

`org.organizations.is_training` (D-223) marks the demo org, and the two consolidated
cross-org reads leave it out.

## The demo org (D-223)

`pnpm demo:org` seeds the `training` org's set-up (HQ, warehouse and showroom, the chart,
three wallets, two suppliers, Steadfast, a size attribute — a seed run as `erp_owner`),
anonymises the repository's synthetic sample files — phones become positional fakes that skip
any number the file holds, names come from a fixed list, money is scaled by 7/10 — and runs
them through the real importers and the opening post. It takes no other directory: the money
scale is a constant in the code, so a real brand's costs would be readable by trainees. The
notify module suppresses every message the training org queues, because its demo numbers are a
real mobile range.

## Risks

- **A brand's export is not a CSV this can read.** The dry run names the row and the column,
  and changes nothing. No importer guesses a column; an unknown column is refused.
- **Cost that is not cost.** `unit_cost_taka` is purchase cost (invariant 5). There is no HTTP
  route; the command prints totals, never rows, and only the operator with database access
  runs it.
- **A second run after a partial failure.** There is no partial failure (check 2), so the only
  second run is of a whole file, which the batch hash makes a no-op.
- **The opening journal posted twice.** The key is the org's, not a client id or a date, and
  `migration.openings` is unique per org.
- **Legacy COD settled later.** A courier statement naming a pre-go-live parcel matches no
  consignment; M12's settlement import has to clear it against the opening receivable
  (follow-up, D-220).
- **A cut-off older than yesterday.** Refused (D-221); a brand that needs one needs a decision.
