# M14a: Data migration and opening balances

Phase 1 · Effort MAX · Depends on: M06–M13 · Gate: G3 · Architecture §7, §8, §25

> Planned on 2026-10-02, before the build, under continuous build mode (no approval
> pause; the plan is still written first).

## Scope

The pilot brand starts with books and stock its accountant will sign. Six importers,
one opening journal, one reconciliation report, and a demo org for training.

Everything here runs **once per brand, before go-live**, by an org admin. That shapes
two choices the rest of the plan follows from: the importers are allowed to be slow,
and they are not allowed to be approximate.

## Out of scope

- M14b's deployment, observability and the go-live runbook.
- Importing anything that is not needed to open the books: campaigns, payroll history,
  message logs. A brand's past SMS is not an opening balance.
- Editing an opening balance after it is posted. A mistake is a reversal journal and a
  new import, like every other posted journal (invariant 2).

## The six importers

Each has `POST /v1/migration/imports/<kind>/dry-run` and `POST .../<kind>`, takes a CSV,
and reports before it writes. In order of dependency:

1. **SKUs** — product, variant, code, selling price. Reuses M06's catalog importer
   through `CatalogApi` rather than restating it; this importer's job is the opening
   _set_, so its report names SKUs it would create and ones that already exist.
2. **Opening stock** — SKU, location, quantity, unit cost. Emits
   `opening_balance` movements, the kind `packages/domain/src/inventory/movements.ts`
   already declares and nothing has ever written.
3. **Supplier dues and advances** — supplier, amount, direction.
4. **Wallet balances** — wallet, amount.
5. **Courier COD in transit** — courier, order reference, amount collected or owed.
6. **Customers** — phone, name, and historical outcomes (delivered, returned) so M13's
   fraud signals start from the brand's real history rather than from zero.

## How the three hard checks are kept

**Check 2, all-or-nothing.** One `withOrg` transaction per commit, with the refusal
thrown from inside it, so PostgreSQL rolls back. Not a loop with a flag: a loop that
validates then writes is still interrupted by a dropped connection halfway, and "some
of these 900 rows are in and I do not know which" is the state that cannot be
recovered from.

**Check 3, idempotency.** A new table `migration.batches` holds
`(org_id, kind, content_sha256)` unique. The commit inserts the batch row first, in the
same transaction; a second run of the same file conflicts and returns the first batch's
result without writing anything. The hash is of the file's bytes, so a re-upload of the
same export is a no-op and an edited file is a new batch.

**Checks 1 and 4, the numbers.** The dry run computes the opening trial balance and the
stock value from the parsed rows alone, in `packages/domain/src/migration`, with no
database. The commit then posts and the reconciliation report reads the result back
through the _modules'_ own reports — `LedgerApi` for the trial balance,
`InventoryApi.valuation` for stock — and refuses to sign off unless they agree to the
poisha. A report that recomputed the numbers itself would agree with itself.

## Data model

New schema `migration`, one tenant table, RLS ENABLE and FORCE, composite tenant FKs,
minimal grants:

- `migration.batches`: `org_id`, `kind`, `content_sha256`, `row_count`,
  `committed_at`, `committed_by`, and a `summary` jsonb holding what was written
  (counts and totals, never a row's contents). Unique on `(org_id, kind, content_sha256)`.
  Append-only: INSERT and SELECT for `erp_app`, no UPDATE or DELETE.

Nothing else. Opening stock becomes `inventory.stock_movements`, opening dues become
journal lines, customers become `sales.customers` — each written by the module that
owns it, through its API. This module owns the _record that an import happened_ and
nothing more.

## Invariant 12, and why this module has ports

A migration module is the one most tempted to write every other module's tables, and it
is the one where that would hurt most: an opening stock row inserted directly would skip
`sku_costs`, so the brand's WAC would start wrong and every later sale's COGS with it.
So each importer calls the owning module:

- `InventoryApi.receiveOpening` (new) for stock and `sku_costs` together.
- `LedgerApi.post` for the opening journal, through a posting rule.
- `CatalogApi` for SKUs, `CustomersService` for buyers, `WalletsApi` for wallets.

`apps/server/src/modules/module-boundaries.test.ts` is the ratchet; `migration` starts
with no debt on it and must stay that way.

## Domain functions and what tests them

In `packages/domain/src/migration`:

- `reviewOpeningStock(rows)`: problems per row (unknown SKU is the caller's to resolve,
  a negative quantity or cost is not), the total quantity, and
  `stockValuePoisha = Σ(qty × unitCost)` through `mulQty`. Property: the total never
  disagrees with the sum of the rows' own products.
- `reviewOpeningBalances(rows)`: the trial balance of the opening journal's lines, and
  `balanced` only when debits equal credits exactly. Property: for any set of rows the
  draft either balances or is refused — never posted.
- `openingJournalDraft(...)` in `packages/domain/src/posting/opening-balance.ts`: the
  posting rule, with the fast-check balance property and a worked example every posting
  rule has (`.claude/rules/money-and-ledger.md`).

## The opening journal

One journal, dated the evening before go-live (a parameter, not `now()`), source type
`opening_balance`, idempotency key `opening_balance:<org>:<asOf>` so a second attempt
returns the first journal. Dr Inventory, Dr wallets, Dr supplier advances, Dr courier
receivable; Cr supplier payables, Cr Opening balance equity. The equity line is the
plug, and it is named rather than derived silently: an accountant signing this needs to
see what the brand is being credited with.

§7's chart has no `opening_equity` subtype; if the seeded chart does not already carry
one, adding it is a decision row plus a §7 table change (`.claude/rules/money-and-ledger.md`).

## Reconciliation report and the demo org

- `GET /v1/migration/reconciliation?asOf=` returns, side by side: the opening journal's
  trial balance, the inventory module's stock valuation, wallet balances, supplier dues
  and courier receivable — each from the owning module — plus a `signedOff` flag the
  accountant's review sets. Check 5's human half is the signature; the machine half is
  that every pair agrees.
- The demo org is seeded by a script from anonymised data: phones replaced by a
  deterministic fake per customer, names replaced from a fixed list, money scaled by a
  constant so totals stay plausible. It is never the pilot brand's data with the names
  removed by hand.

## Risks

- **A brand's export is not a CSV this can read.** The dry run is the answer: it names
  the row and the column, and changes nothing. No importer guesses a column.
- **Cost that is not cost.** Opening stock's `unit_cost_poisha` is purchase cost
  (invariant 5), so it is never returned to a role without `read:cost`, and the
  reconciliation report's stock figure is withheld rather than rounded for those roles.
- **A second run after a partial failure.** There is no partial failure (check 2), so
  the only second run is of a whole file, which the batch hash makes a no-op.
- **The opening journal posted twice.** The idempotency key is derived from the org and
  the as-of date, not from a client id, so a retry cannot create a second journal.
