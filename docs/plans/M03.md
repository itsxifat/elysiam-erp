# M03: Ledger core

Phase 0 · Effort MAX · Depends on: M02b · Architecture §7, §27

Standing approval from the human: build straight through after writing this plan.

## Scope

A double-entry ledger that the database itself refuses to corrupt, plus the
money arithmetic every later milestone leans on:

1. **Money** (`packages/domain/src/money`): the `Poisha` type, `add`, `sub`,
   `sum`, `negate`, `mulQty`, `percentOf` (basis points, half away from zero),
   `allocate` (largest remainder), and parse helpers for taka strings and
   poisha strings. `formatMoney` in `packages/i18n` (৳, lakh/crore grouping,
   optional Bangla digits).
2. **Business dates** (`packages/domain/src/dates`): the Asia/Dhaka calendar
   date of an instant, monthly periods.
3. **Ledger schema** (`ledger`): accounts with subtypes, journals, journal
   lines, periods. The database enforces balance (deferred constraint
   triggers), immutability (REVOKE plus triggers), the period lock, and
   idempotency (unique index).
4. **Chart of accounts** seeded per org from `packages/db/src/seed/coa-template.ts`,
   with a hand-cash wallet per branch. The seed stays idempotent.
5. **`ledger.post(tx, draft)`** (idempotent) and **`reverse(journalId, reason)`**,
   exposed through `ledger.api.ts`.
6. **Periods**: close by org_admin/accounts; reopen only through an approved
   `period_reopen` request, which only super_admin may decide.
7. **Queries**: account ledger, trial balance, party balance, cash book per
   wallet, day book by business date.
8. **One posting rule**, cash in (`Dr W / Cr income`), end to end through an
   API endpoint.
9. Follow-ups assigned here: an ESLint rule banning `toFixed` / `parseFloat`
   outside `packages/domain/src/money` (M00), and the tenancy guard checking
   every policy on a table rather than counting (M02a).

### Out of scope (logged as follow-ups)

- Any other posting rule (supply, delivery, POS, payroll…): their milestones.
- An HTTP route for manual reversal. `reverse()` is a service function other
  modules call; a user-facing reversal needs maker-checker and a UI (M14a).
- Creating accounts through the API, and wallets for branches created after
  the seed (no branch-creation API exists yet).
- P&L, balance sheet, aging, consolidated super-admin views (M14a / M24).
- Back-dating approval (`back_dated_entry`): the cash-in route takes no date
  from the client, so nothing can be back-dated yet.
- UI screens (M05 builds the console kit; M14a the accounting screens).
- Partitioning journals. §7 does not call for it; volumes at five brands do
  not need it yet, and composite FKs into a partitioned table would need the
  partition key in every reference.

## Data model (migration generated with `pnpm db:generate`, plus hand SQL)

`ledger` schema, every table tenant-scoped with `tenantTableSql()`:

- `ledger.accounts`: `id, org_id, code, name, class, subtype, normal_balance,
branch_id, party_type, is_system, is_active, timestamps`.
  Unique `(org_id, code)`, unique `(org_id, id)`. Composite FK
  `(org_id, branch_id) → org.branches`. CHECK: `wallet_cash` needs a branch.
  Grants: select, insert, update (no delete). A trigger freezes `org_id, code,
class, subtype, normal_balance, branch_id, party_type, is_system`.
- `ledger.journals`: `id, org_id, business_date, source_type, source_id,
idempotency_key, memo, reverses_journal_id, content_hash, created_by,
created_txid, created_at`. Unique `(org_id, idempotency_key)`, unique
  `(org_id, id)`, partial unique on `reverses_journal_id`. Composite FK for the
  reversal. APPEND_ONLY grants.
- `ledger.journal_lines`: `id, org_id, journal_id, line_no, account_id,
branch_id, party_type, party_id, debit_poisha, credit_poisha, memo`.
  CHECKs: both sides ≥ 0, exactly one > 0. Composite FKs to journals,
  accounts, branches. APPEND_ONLY grants.
- `ledger.periods`: `id, org_id, starts_on, ends_on, status, closed_at,
closed_by, reopened_at, reopen_approval_id, timestamps`. Unique
  `(org_id, starts_on)`. Composite FK `(org_id, reopen_approval_id) →
approvals.approval_requests`. Grants: select, insert, update (no delete).

Triggers (hand-written migration, `--custom`):

- Deferred constraint triggers on journals and lines: ≥ 2 lines, Σdebit =
  Σcredit > 0, checked at commit.
- `before update or delete` on journals and lines: raise, for every role.
- `before insert` on journals: stamps `created_txid = pg_current_xact_id()`
  and applies the **period lock** (shared advisory lock on the org+month, then
  refuses a closed period).
- `before insert` on lines: the journal must have been created in this same
  transaction (so no line can be added to a posted journal), the account must
  be active, party and branch must match the account.
- `before insert or update` on periods: inserts only as `closed`; the only
  transitions are open→closed and closed→open; closed→open requires an
  approved `period_reopen` for this period raised and decided after the close.
- Close and reopen take the exclusive advisory lock, so a close cannot
  interleave with an in-flight post.

Guard: add journals and lines to `APPEND_ONLY_TABLES`; the tenancy guard now
examines **every** policy on a table (declared extras only).

## Domain (pure, tested)

- `money/`: see scope. fast-check: `allocate` sums exactly, parts differ by at
  most one unit of weight share; `percentOf` against a reference computed with
  exact rationals; `.5` boundaries positive and negative; overflow refused.
- `dates/`: `businessDate(instant)`, `periodOf(date)`, `isIsoDate`.
  Check 7 is a unit test.
- `ledger/`: account classes and subtypes (class, normal balance, party type,
  wallet, cost-bearing), `JournalDraft`, `validateJournalDraft`,
  `idempotencyKey`, `canonicalDraft`, `reverseDraft`, `trialBalance`.
- `posting/cash-in.ts`: the cash-in rule, with a fast-check balance test and a
  hand-computed worked example.

## API (all `/v1/ledger/*`)

| Route                       | Ability             | Notes                                                                              |
| --------------------------- | ------------------- | ---------------------------------------------------------------------------------- |
| `GET accounts`              | read LedgerReport   | branch-scoped                                                                      |
| `GET accounts/:id/ledger`   | read LedgerReport   | cost accounts withheld from non-cost roles                                         |
| `GET trial-balance`         | read LedgerReport   | lines filtered by branch scope                                                     |
| `GET party-balances`        | read LedgerReport   | supplier balances withheld without read:cost                                       |
| `GET day-book`              | read LedgerReport   | by business date range                                                             |
| `GET wallets`               | read Wallet         | branch-scoped                                                                      |
| `GET wallets/:id/cash-book` | read Wallet         | branch-scoped                                                                      |
| `POST cash-in`              | update Wallet       | posts `Dr W / Cr other_income`                                                     |
| `GET periods`               | read LedgerPeriod   |                                                                                    |
| `POST periods/close`        | update LedgerPeriod | month must have ended                                                              |
| `POST periods/reopen`       | update LedgerPeriod | raises `period_reopen`; super_admin decides; reopens in the decision's transaction |

`LedgerPeriod` is a new subject (matrix change, decision row). Every mutation
writes its own audit row in its transaction. Errors carry a stable `code` from
`packages/contracts/src/errors.ts` (seeded here ahead of M04's problem+json).

No events or realtime payloads: M04 builds the outbox; `wallet.balance_changed`
lands then.

## Assumptions (new decisions.md rows)

Poisha as a branded bigint; ledger immutability design; period model and
reopen executor; idempotency conflict on differing content; `LedgerPeriod`
subject and cash-in as `update Wallet`; CoA template details
(`operating_expense` subtype); cost-bearing accounts withheld from non-cost
roles; cash-in categories and server-side business date; error codes seeded;
no reversal route; guard checks every policy; the float lint rule.

## Risks

- A trigger that looks right but is bypassable (lines added to a posted
  journal, a reopen by direct UPDATE, a close racing a post). Each gets an
  adversarial test against real Postgres.
- Deferred triggers and RLS: the check runs at commit as the invoker; it must
  fail closed if the org context changes mid-transaction.
- `resetTenantData` truncating with cascade now reaches ledger tables.
- Cost leakage through ledger reports for branch managers.
