# M33: The website's catalog and content, run from the ERP

Wave 3 · Depends on: M31 (can be built beside it) · Architecture §31 (new) · Decisions D-500 to D-519

> Planned on 2026-10-05 from the owner's instruction: "every child ERP will also act as their
> individual website's backend admin panel … we control order, customer, lead, offers,
> discount, website interfaces, everything … for now we will be setting up the
> elysium-lifestyle.bd website … from now their website's admin panel will be maintained from
> the ERP, no more from the admin panel." The inventory of the old admin panel (31 screens,
> 112 API routes, 20 Mongo models) is summarised in `docs/plans/wave3.md`.

## What this is, in plain words

The brand's website stops keeping its own products, categories, banners and menus. The ERP
keeps them, staff edit them in a new **Website** section of the console, and the website reads
them from the ERP. This milestone covers everything a shopper **looks at**. Buying (cart,
checkout, accounts, payment) is M34; offers, landing pages and the marketplace link are M35;
rewriting the website itself is M36.

## Scope

1. **Product fields for the web** (D-500), on `catalog.products`:
   - `web_visible` (published on the website; separate from `status`, so a product can be
     sold at the till and the desk without being on the site), `featured`, `new_arrival`,
     `gender` (men, women, kids, unisex, or none), `material`, `care_instructions`, `tags`
     (text array, lower-case), `size_chart_id`, `seo_title`, `seo_description`, and
     `previous_slugs` (old addresses that redirect, written by a trigger on a slug change);
   - a rich description stays the existing `description`, lengthened to 20,000 characters
     (the old site's descriptions are HTML-free text with line breaks).
2. **Category fields for the web** (D-501): `image_file_id`, `description`, `gender`,
   `featured`, `web_visible`. `position` and `is_active` already exist.
3. **Size charts** (D-502): `storefront.size_charts (name, columns text[], rows jsonb)`; a
   product points at one.
4. **Website settings** (D-503), one `storefront.settings` row per brand, edited on
   **Website → Settings** in sections:
   - site info (name, logo, merchant id printed on labels, WhatsApp, phone, email, address);
   - social links; announcement bar; promo banner; testimonials;
   - shipping rule: free shipping on or off, free-shipping threshold, and the fee for each
     website zone (inside Dhaka, suburbs, outside Dhaka) mapped onto the ERP's delivery zones;
   - which payment methods the checkout offers (COD, SSLCommerz) — the SSLCommerz credentials
     themselves are M34's, encrypted;
   - where web stock is sold from: one or more stock locations (default: the main warehouse).
5. **Hero slides and the menu** (D-504): `storefront.hero_slides` (desktop image, mobile image,
   link, position, active) and `storefront.nav_items` (type: link, category or dropdown; label;
   link or category; highlighted; active; position).
6. **Old ids kept** (D-505): `storefront.legacy_ids (kind, legacy_id, erp_id)`, filled by M36's
   importer, read by redirects and by the marketplace connector (M35), which addresses variants
   by the old site's ids.
7. **The storefront read API** (D-506), `/storefront/v1/*`, server to server only:
   - authenticated like the intake API: a site key `pk_…` plus an HMAC over
     `timestamp.method.path.query` (GET) or the raw body (POST), ±5 minutes; issued on
     **Website → Connection**; the old intake keys keep working for intake;
   - `GET catalog/products` (filters: category with its subtree, gender, tags, size, price
     range, on sale, featured, new arrival, search; sort; cursor pagination), `GET
catalog/products/:slug` (variants with price and **available quantity at the web
     locations**, images, size chart, related products, and a redirect answer for an old
     slug), `GET catalog/categories` (tree), `GET catalog/search?q=`, `GET site` (settings,
     hero, menu, announcement, testimonials in one cached response), `GET size-charts/:id`;
   - responses carry money in poisha and taka strings both; no cost field can appear
     (`serializeFor` with the storefront's own allow-list, like the reseller list in §6);
   - `ETag` and `Cache-Control: max-age=30, stale-while-revalidate=300` on reads.
8. **Public images** (D-507): product, category, hero and logo images are served from a public
   path (`/media/<file id>/<variant>`) with long-lived caching, resized to the old site's sizes
   by the existing image pipeline; the files module marks these purposes public.
9. **Console: Website section** (`/website`):
   - Settings (the sections above), Hero slides (drag to reorder, desktop and mobile images),
     Menu (nested items, drag to reorder), Size charts (a grid editor), Connection (site keys);
   - on the product page: a **Website** card (shown on the site, featured, new arrival,
     gender, tags, size chart, SEO, material, care) and a "View on website" link;
   - on Catalog setup: the category's website fields.
   - Permission: a new `Storefront` subject; `org_admin` and `marketing` manage it,
     `sales` reads it.

## Out of scope

- Cart, checkout, customer accounts, payments, emails (M34).
- Flash sales, discount rules beyond today's promo codes, landing pages, custom links, tracking
  pixels, the ncom connector, the scanner app (M35).
- Changing the website (M36).

## Rules (packages/domain)

- `availableForWeb(levels, webLocations)`: sum of `on_hand − reserved` over the web locations,
  never negative.
- `storefrontPrice(sku, flashOffers?)`: shelf price now; M35 adds the flash offer.
- Slug history: a renamed slug keeps its old one; an old slug that becomes another product's
  current slug stops redirecting.

## Data model

New schema `storefront` (tenant tables, RLS ENABLE and FORCE, composite foreign keys):
`settings`, `hero_slides`, `nav_items`, `size_charts`, `legacy_ids`. New columns on
`catalog.products` and `catalog.categories`. One migration.

## Risks

- A cost field reaching the website: the storefront serializer is an allow-list, and the cost
  sweep test gains the storefront routes.
- Stock shown on the site that the desk then sells: availability is read live from inventory,
  never cached longer than 30 seconds, and M34 reserves at checkout.

## Acceptance checks

1. A product marked hidden is absent from every storefront list and its detail answers 404;
   shown, it appears with each size's available quantity at the web locations only.
2. Renaming a product's slug makes the old slug answer a redirect to the new one.
3. A storefront request with a bad signature, a stale timestamp or a revoked key is 401; no
   storefront response contains a cost field (cost sweep).
4. Website settings, hero, menu and size charts round-trip through the console (stack spec
   with screenshots in `docs/review/M33/`).
5. `pnpm verify` green; ledger-auditor on the tenancy diff.
