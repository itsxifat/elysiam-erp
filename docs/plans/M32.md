# M32: The mother ERP

Wave 3 · Depends on: M31 · Architecture §30 (new) · Decisions D-480 to D-499

> Planned on 2026-10-05 from the owner's instruction: "from mother ERP the super admin can
> handle all the child ERPs' data and see them, and in mother ERP we can see combined progress
> … every single metric and number and data, everything." Separate server, separate domain.

## What this is, in plain words

A separate website and server for the owner and the people the owner trusts. It shows every
brand's numbers side by side and added together: orders, sales, profit, cash, stock, COD, ad
spend, staff performance. From any brand's page, one button opens that brand's ERP signed in as
the owner, with full control there.

The brands never call the mother and never learn it exists. The mother reaches each brand's
database read-only, the same way a reporting tool would, and signs the owner into a brand with
a one-time link that the brand checks with a public key.

## Shape (D-480)

- `apps/mother-server`: NestJS on Fastify, API and worker entrypoints, its own Postgres database
  (`elysium_mother`) and its own Drizzle schema and migrations under
  `apps/mother-server/src/db`. It imports `@elysium/domain`, `@elysium/contracts` and
  `@elysium/db`'s table definitions for reading brand databases, never the brand server's code.
- `apps/mother-console`: React + Vite, the same `@elysium/ui` kit, tokens, i18n (bn + en) and
  `<Money>`.
- Nothing from the mother is in a brand image or a brand bundle.

## How the mother reads a brand (D-481)

- Each brand database already has the `erp_analytics` role: SELECT only, every row. The mother
  keeps one connection string per brand for that role, encrypted at rest (AES-256-GCM,
  `MOTHER_SECRETS_KEY`).
- The network path is an SSH tunnel from the mother server to the brands server, to a
  tunnel-only account limited by `permitopen` to the brands' Postgres ports (D-482). Postgres
  never listens on a public address.
- The mother checks each brand's applied migration count against the one it was built with and
  shows "version mismatch" instead of reading a schema it does not know.

## What the mother keeps (its own database)

- People: Better Auth users, sessions, accounts, two-factor (TOTP **required for everyone**),
  verifications. No self sign-up; `pnpm mother:bootstrap` creates the first owner; owners invite
  others.
- `brands`: slug, display name, admin URL, encrypted read connection, owner-link key pair (the
  private key encrypted; the public key shown once to paste into the brand's env), status, last
  pull time and error.
- Pulled figures, refreshed every 10 minutes by the worker and on demand:
  - `brand_daily` (the brand's `analytics.daily_org` per business date),
  - `brand_daily_channel`, `brand_daily_campaign`,
  - `brand_snapshot` (taken at each pull): cash by wallet kind, stock value, COD held by
    couriers, supplier payables, receivables, open orders by status, staff head count, active
    SKUs, low-stock SKUs.
- `audit_log`: every sign-in, owner link issued, brand added or changed.

## Screens

1. **Overview**: today, this week, this month and a chosen range. Totals across brands and a
   row per brand: orders placed, confirmed, delivered, returned, cancelled; delivered revenue;
   gross profit; ad spend, ROAS, cost per delivered order; delivery success and return rate;
   cash, stock value, COD outstanding. A trend chart per metric with a line per brand.
2. **Leaderboard**: M24's rules (D-322), now across brands, computed from the pulled rollups.
3. **Brand page**: the brand's figures and trend, plus live lists read straight from its
   database: latest orders, top products, low stock, wallets, courier COD, staff. "Open
   <brand> ERP" signs the owner in there (M31's owner link).
4. **Accounts across brands**: the consolidated wallets and P&L that M31 removed from the brand
   ERP, built from each brand's ledger.
5. **Brands** (settings): add a brand, test its connection, rotate its owner-link key.
6. **People**: invite an owner, remove one, reset their two-step login (another owner must
   approve).

## Domain

- Aggregation and the leaderboard reuse `packages/domain/src/analytics` (pure, tested).
- New pure functions: summing per-brand snapshots, range comparisons, the owner-link assertion
  builder (shared with M31's verifier).

## Risks

- Reading a brand's database couples the mother to its schema. Same repo, deployed together, and
  the migration-count check refuses a mismatch rather than misreading.
- A brand that is down: its last pulled figures stay, marked with their age.
- The mother holds the keys to every brand. It is the most sensitive system: TOTP for all,
  short sessions (8 hours), its own domain, no other app on its origin, every action audited.

## Acceptance checks

1. With two brand databases seeded by `preview:seed --brand`, the overview's totals equal the
   sum of each brand's own dashboard for the same range.
2. "Open brand ERP" signs the owner into the brand; the link cannot be reused.
3. The mother's read role cannot write to a brand database (tested).
4. A brand database that is unreachable shows its last figures with their age and an error, and
   the other brands still load.
5. No request from a brand's browser, server or worker goes to the mother (a test fixes the
   brand's outbound host list).
6. `pnpm verify` green; ledger-auditor on the consolidated money reads.
