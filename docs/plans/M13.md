# M13: Fraud check v1

Phase 1 · Effort XHIGH · Depends on: M10 · Gate: G2 · Architecture §5, §10

> Written on 2026-09-30, after the build. M13 was built on 2026-09-26 without a
> plan file. This records the plan as executed.

## Scope

Before confirming, an agent sees how trustworthy a phone number is across all
five brands. A brand learns from the others' returns without seeing a single
order of theirs.

## Out of scope

- Advance-payment rules driven by the score, and fraud v2 signals (M17).
- Reseller lookups. Whether a reseller may check a number is an open client
  question.

## Data model

Schema `fraud`, migrations 0045 to 0047.

- `phone_signals`, `provider_checks`: **cross-org, with no `org_id` and no RLS**
  (D-105). This is the one deliberate exception to invariant 4. They hold a
  keyed hash and counters, never a number, an order or a name.
- `rules`, `phone_flags`, `overrides`, `order_phones`: ordinary tenant tables.
- A manual flag's reason and author stay in the tenant table. The cross-org row
  holds only the time and severity (D-106).

## Domain functions and what tests them

In `packages/domain/src/fraud`:

- `score.ts`: the trust score. Table-driven tests for the five named cases, and
  a property that the score stays inside its range.
- `bands.ts`: per-org allow, warn and block bands (D-011).

In the server module:

- `phone-hash.ts`: HMAC with `FRAUD_PHONE_HASH_KEY`. No fallback. A missing or
  short key stops the process at boot (D-108).
- `providers/provider-gateway.ts`: a TTL cache, throttling, and one failure
  branch for every way a provider can fail.

## API, events, jobs and screens

- Routes under `/v1/fraud`: check, rules, flags, clear flag, order overrides.
- `fraud.api.ts` is bound to the orders module's `FRAUD_GATE` port.
- A subscriber maintains the counters from `order.status_changed`.
- Event: `order.fraud_flagged`.
- Job: `fraud.refresh_provider`.
- The badge and its reasons render in the order desk's badge slot.

## Decisions

D-010, D-011 and D-105 to D-111. The ones that protect privacy: no phone number
and no hash appears in any response, event or audit row (D-107), and a provider
outage costs zero points and says so on the badge (D-109).

## Risks that mattered

- **The gate was bound under the wrong Symbol.** Orders kept a permissive
  default and no order was ever blocked, with every test green. Fixed by binding
  `FRAUD_GATE` to the fraud API through the module import.
- **Reads returned 500 for reseller and branch manager.** The fraud subject has
  no row dimension, so scoped roles needed an explicit declaration (D-111).
- **The counters depended on a dispatcher that did not deliver.** See D-131.
- **A default hash key** would silently make every number a new person.
