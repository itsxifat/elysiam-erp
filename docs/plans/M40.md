# M40: Account and two-step sign-in management (brand side)

Wave 3 · Depends on: gaps-users-auth (D-400 to D-410), M31 (D-473), trust (D-654 to D-689) ·
Decisions D-691 to D-700 · Branch `m40-accounts` from `integration-wave2` (75dbe8e2)

> Asked for by the owner on 2026-10-11: "we need better account management, two factor
> management, user friendly and more options fully. also turn on and off two factors, reset
> and other stuffs."

## What this is, in plain words

1. **My account** (`/account`, from the account menu): everyone can change their name, change
   their password (and sign out their other devices while doing it), see whether two-step
   sign-in is on and whether their role requires it, set it up, move it to a new phone, get new
   backup codes, turn it off when nothing requires it, and see every device they are signed in
   on, signing any of them out.
2. **Settings → Security** (super admins only): one switch per role saying whether two-step
   sign-in is required for it in this brand. Super admins always need it. Switching a role on
   asks the people in it who have not set it up to do so at their next click; switching it off
   never turns anyone's two-step off.
3. **Staff**: each person's two-step state and last sign-in, plus "Sign out everywhere" and,
   for people whose role does not require it, "Turn off two-step". The lost-phone reset with a
   second admin (D-404) stays as it is.

## Scope

- Pure policy in `@elysium/domain/iam` (`two-factor-policy.ts`): the switchable roles, the
  default (today's `TWO_FACTOR_REQUIRED_ROLES`: org_admin, accounts, investor), reading a stored
  value safely, "does this person need two-step", "may they turn it off", and a user agent /
  address describer for the devices list (`devices.ts`).
- The one place that decides "must this person use two-step": `twoFactorRequirement` and
  `mustEnrolTwoFactor` in `packages/db/src/auth`, reading each brand's policy from
  `org.settings` (`security.two_factor`). Used by the enrolment wall, the scanner sign-in and
  its device check, the Staff list and the account page.
- `iam.two_factors.enabled_at` (migration 0140) so "set up on" can be shown.
- Server (iam module): `GET /v1/account`, `PATCH /v1/account/profile`,
  `GET /v1/account/sessions`, `DELETE /v1/account/sessions/:id`,
  `POST /v1/account/sessions/sign-out-others`, `POST /v1/account/two-factor/replace`,
  `POST /v1/account/two-factor/replace/confirm`, `POST /v1/account/two-factor/turn-off`,
  `GET` and `PUT /v1/security/two-factor-policy`, `POST /v1/users/:id/sign-out-everywhere`,
  `POST /v1/users/:id/two-factor/turn-off`. Better Auth's `/two-factor/disable` HTTP path is
  closed. Password change and new backup codes use Better Auth's own endpoints.
- Console: the account page (lazy route), Settings → Security, Staff additions, a walled
  session opening on the set-up screen, a locally drawn QR code (uqr).
- Out of scope: email or SMS for codes (D-212), passkeys, the mother ERP's own accounts
  (`apps/mother-*`, another builder), a per-brand "remember this device" policy.

## Data model

- `org.settings` row `security.two_factor` = `{ "requiredRoles": [...] }` per brand. No row
  means the default. A tenant table already (RLS ENABLE and FORCE, erp_app CRUD).
- `iam.two_factors.enabled_at timestamptz` + trigger `iam.two_factors_stamp_enabled_at`:
  stamped when a factor becomes verified or its secret changes while verified.
- A replacement secret waits in `iam.verifications` (`two-factor-replace:<user id>`, 10
  minutes), encrypted with Better Auth's own symmetric encryption, never in clear.

## Acceptance checks

1. Change password: the old password stops working, the new one signs in; with "sign out my
   other devices" the other sessions end and this one stays; audited.
2. Set up on a new phone: needs the password and a current code; the old code keeps working
   until a code from the new phone confirms; then only the new one works; audited.
3. New backup codes: needs the password; the old codes stop working.
4. Turn off: allowed for a role nothing requires (two-step then off, sign-in asks no code);
   refused for a required role, for a super admin, with a wrong password or code; Better
   Auth's `/two-factor/disable` is closed.
5. Devices: lists this and other sessions with the address masked; sign out one; sign out all
   others; the current session cannot be ended from the list; audited.
6. Security setting: super admin only; turning sales on walls a sales user without two-step at
   their next request; turning it off lets them through; nobody's factor is removed; audited
   with before and after.
7. The scanner sign-in and a scanner device follow the policy.
8. Staff: sign out everywhere (not yourself, super admins protected, owners never) and turn off
   two-step (refused when required; a second admin for money roles as D-404) — permissions on
   real Postgres; route-matrix fixtures for every new route.
9. Console unit tests for the account page parts; typecheck, lint, format, check:routes,
   check:i18n, check:api-client, check:migrations, check:schema, check:bundle.
