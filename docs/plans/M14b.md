# M14b: Deployment, observability, go-live kit

Phase 1 · Effort XHIGH · Depends on: M14a · Gate: G3 · Architecture §25, §26, §28 (and §5's roles)

> Planned on 2026-10-02, before the build, under continuous build mode (no approval
> pause; the plan is still written first). The owner asked for it fast and lean: what the
> acceptance checks need, nothing extra. No staging server exists yet (G3 is open), so
> everything that can be built and tested without one is built here, and checks 1–3 are
> written as runbooks a person executes on staging. Chatwoot, `apps/sites` and
> `apps/extension` are out of scope (D-290 to D-292), so none of them is deployed.

## Scope

1. **Images.** One production image for the server (multi-stage, `pnpm deploy`, non-root
   `node` user). The API and the worker are the same image with a different command, as
   §3 says they are the same codebase. Fonts for PDFs travel in the image.
2. **Kamal.** `infra/kamal/deploy.yml` with a staging destination: the `api` role behind
   kamal-proxy (health-gated), the `worker` role (no proxy, the only role holding the owner
   URL), and Valkey and Gotenberg as accessories on the private Docker network. Secrets
   only as references in `.kamal/secrets*` (environment or a secret manager); placeholder
   hosts.
3. **Migrations as a release step.** A `pre-deploy` hook runs `db:migrate` from the new
   image, as `erp_owner`, before any new container boots. The seed is not a release step.
4. **Database roles on managed Postgres.** `bootstrap.sql` today assumes a superuser.
   Managed Postgres has none, and PostgreSQL 16+ refuses `ALTER ROLE … NOSUPERUSER`,
   `NOREPLICATION` and `NOBYPASSRLS` from a non-superuser even when they change nothing
   (verified on 17.11). Make it clear only the attributes a role actually has, and prove it
   with a test that bootstraps and migrates as a CREATEROLE-only admin.
5. **Cloudflare Pages** for console, portal and pos: direct upload with `wrangler pages
deploy`, and a generated `_headers` per app (CSP with the inline script's hash,
   `connect-src` from the build's API URL, frame and sniffing headers, immutable assets).
6. **Observability**, each off unless configured:
   - Sentry (server, errors only) through one `reportError` seam: 5xx in the problem
     filter, dead-lettered jobs, a failed boot. `beforeSend` scrubs secrets and phones.
   - OpenTelemetry traces and metrics over OTLP, started from `--import ./dist/instrument.js`
     only when an OTLP endpoint is set; URL attributes are scrubbed (no query, phones masked).
   - pino: phones masked in every message and field, credential-named keys removed at any
     depth (the audit log's `redact`), tested.
   - `/health/ready`: database as `erp_app`, the pg-boss schema, Valkey. 503 names the
     failing check and nothing else.
   - Uptime and alert guidance in a runbook.
7. **Runbooks** in `docs/runbooks/`: deploy (first-time provisioning and routine), rollback,
   restore (PITR and the logical dump, with a drill log), secret rotation, courier outage,
   month-end close, go-live (M14a's seed and reconciliation steps, M16's queue policy),
   monitoring. The existing `queue-policy.md` stays.
8. **Security review** of the deployment surface (check 4), high findings fixed.

## Out of scope

- Executing checks 1–3: they need the owner's staging (G3). The runbooks say exactly what
  to run and what to record.
- Browser Sentry in the SPAs, and source-map upload (follow-up; §26 asks for it, it needs
  a DSN, a CSP entry and the bundle budget looked at).
- CI deploy workflows. The commands are in the runbooks; wiring them to GitHub Actions
  needs the owner's Cloudflare and registry tokens.
- Alert rules in a specific vendor; the runbook names the signals and thresholds.

## Design notes

- **TRUSTED_PROXY_COUNT = 2** in production: Cloudflare appends the client to
  `X-Forwarded-For`, kamal-proxy appends Cloudflare's edge. Valid only if the VMs accept
  80/443 from Cloudflare's ranges alone, which the deploy runbook makes a step.
- **TLS:** Cloudflare Full (strict) with a Cloudflare Origin CA certificate given to
  kamal-proxy as `certificate_pem` / `private_key_pem` secrets; `forward_headers: true`.
- **Backups:** `pg_dump` as `erp_owner` fails under FORCE RLS ("query would be affected by
  row-level security policy", verified), and a CREATEROLE-only admin can neither read the
  schemas nor create a BYPASSRLS role. The logical dump runs as `erp_backup` (LOGIN,
  BYPASSRLS, `pg_read_all_data`), created by an admin that holds BYPASSRLS; PITR is the
  primary path. Rehearsed locally on a throwaway Postgres 17.
- **Valkey** holds rate-limit counters and the Socket.IO adapter's channels only, so it
  runs without persistence and is never published on a host port.

## Risks

- **A deploy that runs the wrong migrations.** The hook runs the new image's migrate
  before boot; a failure aborts the deploy (Kamal stops on a non-zero hook). Migrations are
  forward-only (invariant 9), so the rollback runbook rolls code back, never schema, and
  says so before anyone needs it.
- **The owner URL reaching the API.** Only the worker role's env carries
  `DATABASE_OWNER_URL`; the API's never does.
- **Personal data in telemetry.** Sentry events, spans and logs all pass a scrubber that is
  tested with planted phones and tokens.
- **A CSP that breaks the console.** The hash is computed from the built `index.html`, and
  the POS offline e2e runs against `vite preview` with the same headers.
