# M01: Database core and multi-org isolation

Branch: `m01-database-core` · Effort MAX · Architecture §3, §5 · Depends on M00 (done, merged)

## Scope in my own words

Make it impossible for one brand to see another brand's data, and prove it with tests that run against real PostgreSQL.

This is the milestone where a mistake is worst, because the failure is silent. A broken permission check throws an error somebody notices. A broken row-level security policy returns rows — the wrong ones — and everything downstream looks like it is working. Oura's accountant sees Orvo's cash, and nothing in the logs says so. Every later milestone builds on the assumption that this one is right, so the tests here have to be adversarial rather than confirmatory: not "can org A read its own rows", but "given a determined attempt, can org A reach org B's rows by any route the application exposes".

### Two findings from probing the running database before planning

I tested the architecture's stated design against the live container rather than assuming it works. Two things do not hold as written.

**1. `erp_owner` is a superuser in the dev container, and superusers bypass `FORCE ROW LEVEL SECURITY` entirely.** M00's compose file sets `POSTGRES_USER: erp_owner`, which makes it the cluster superuser. I confirmed: with a policy that should have rejected it, an insert with no `app.org_id` set succeeded, and a select that should have returned 0 rows returned 1. Every isolation test written against that role would pass while proving nothing, and dev would behave differently from a managed production Postgres where `erp_owner` is an ordinary role.

Fix: the container superuser becomes `postgres`, and `erp_owner` is created by bootstrap as a **non-superuser** owner. I verified that under a non-superuser owner, `FORCE RLS` binds correctly — the uncontexted insert is rejected with `new row violates row-level security policy`.

**2. The policy SQL in architecture §5 raises an error instead of returning zero rows on any reused connection.** §5 specifies `using (org_id = current_setting('app.org_id', true)::uuid)` and states that an unset `app.org_id` yields NULL and therefore zero rows. That is only true for a connection that has _never_ set it. `set_config(..., true)` is transaction-local, so after the transaction commits the GUC reverts to the empty string, not to unset — and `''::uuid` raises `invalid input syntax for type uuid: ""`. On a pooled connection, which is every connection in production after its first request, the policy errors.

Erroring is fail-closed, so this is not a data leak. But acceptance check 2 requires _zero rows_, not an error, and a policy that throws on ordinary pool reuse is not something to build 29 milestones on top of. Fix: `using (org_id = nullif(current_setting('app.org_id', true), '')::uuid)`. I verified this returns 0 rows both on a fresh session and after a set-then-reset cycle, while still blocking cross-org reads, writes and updates.

Both fixes need a decisions.md row, and the second needs an architecture §5 correction.

### Explicitly out of scope

- Authentication, users, memberships, sessions — all M02a. `iam` gets no tables here.
- The permission matrix, `serializeFor`, audit, approvals — M02b.
- Ledger, inventory, catalog, orders: no business tables. `org` and `ref` only.
- Branch-level scoping (`branch_id` filtering). The column exists where §5 says it should; enforcing branch scope is a permissions concern, M02b.
- Full upazila/thana coverage if no authoritative source is available — see Risks.

## Data model changes

### Schemas

| Schema | Contents                                                              | Tenant?                     |
| ------ | --------------------------------------------------------------------- | --------------------------- |
| `org`  | `organizations`, `branches`, `locations`, `settings`, `feature_flags` | mixed — see below           |
| `ref`  | `divisions`, `districts`, `thanas`                                    | no, global (§5 exception 5) |

`ref` is new; architecture §3's module map has no home for global geography and putting it in `org` would make the tenancy guard ambiguous. New decision row.

**`org.organizations` is deliberately not tenant-scoped.** It is the org list, which §5 exception 5 names as global. Which orgs a given user may _see_ is a membership question, and membership arrives in M02a. Until then it is readable by the app role and writable only by the owner.

### Tables

- `org.organizations` — `id`, `slug` (unique, natural key for idempotent seeding), `legal_name`, `display_name`, `brand` jsonb (D-034), `timezone` default `Asia/Dhaka`, `is_active`, timestamps. Global.
- `org.branches` — `id`, `org_id`, `code` (unique per org), `name`, `kind` (`hq | showroom | warehouse`), address fields, `is_active`, timestamps. **Tenant.**
- `org.locations` — `id`, `org_id`, `branch_id`, `kind` (`warehouse | showroom | damaged | in_transit`), `name`, `is_active`. **Tenant.** Only the columns §8 needs; stock itself is M07.
- `org.settings` — `id`, `org_id`, `key`, `value` jsonb, unique `(org_id, key)`. **Tenant.**
- `org.feature_flags` — `id`, `org_id`, `key`, `enabled`, `value` jsonb, unique `(org_id, key)` (D-031). **Tenant.**
- `ref.divisions` / `ref.districts` / `ref.thanas` — `id`, `code`, `name_en`, `name_bn`, parent FK. Global.

Every tenant table: `org_id uuid not null references org.organizations(id)`, indexed, plus RLS ENABLE and FORCE with the corrected policy.

### Roles, and who creates them

The chicken-and-egg problem: migrations run as `erp_owner`, but somebody has to create `erp_owner`. Bootstrap is therefore a separate, once-per-database step run as the cluster superuser, and it is the only thing that ever needs superuser.

| Role            | Created by | Rights                                                                                                                                                       |
| --------------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `erp_owner`     | bootstrap  | Owns every object. **NOSUPERUSER, NOBYPASSRLS** — the whole point.                                                                                           |
| `erp_app`       | bootstrap  | The running app. NOSUPERUSER, NOBYPASSRLS, NOCREATEROLE. SELECT/INSERT/UPDATE/DELETE on tenant tables; INSERT/SELECT only on append-only tables from M03 on. |
| `erp_analytics` | bootstrap  | SELECT only, with a second policy permitting all orgs. No write grant anywhere.                                                                              |

Four connection URLs, because they are four different privilege levels and collapsing them is how the app ends up running as owner:

- `DATABASE_URL` — `erp_app`, the running app
- `DATABASE_OWNER_URL` — `erp_owner`, migrations and seed
- `DATABASE_ANALYTICS_URL` — `erp_analytics`
- `DATABASE_ADMIN_URL` — superuser, used only by `pnpm db:bootstrap`

### Migrations

Drizzle generates table DDL, but RLS policies, roles, grants and the analytics policy are not expressible in a Drizzle schema. So each migration pairs generated DDL with a hand-written SQL file, and `tenantTable()` in `packages/db/src/rls.ts` emits the ENABLE/FORCE/policy/grant block so no table can get a subtly different one. The guard test is what stops anyone bypassing the helper.

## Domain functions and tested invariants

No `packages/domain` work — M01 is infrastructure. The invariants and how each is proven:

| Invariant                                                                          | Test                                                                                                          |
| ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Org A cannot read, insert, update or delete org B rows, via Drizzle **or** raw SQL | Integration, real Postgres, per tenant table and per verb                                                     |
| No context set ⇒ zero rows, **not an error**                                       | Integration, including the pooled set-then-reset path that currently errors                                   |
| `erp_app` cannot `SET ROLE`, disable RLS, or bypass policies                       | Integration, asserting the specific error for each                                                            |
| `erp_analytics` reads every org and cannot write                                   | Integration, asserting a write failure per verb                                                               |
| Every table in a tenant schema has `org_id`, RLS enabled and FORCE                 | Guard test enumerating `pg_class`/`pg_policies` — stays in the suite for good, and is what makes M02–M30 safe |
| Migrate + seed twice is a no-op                                                    | Integration, comparing row counts and checksums across two runs                                               |
| Concurrent writers in different org contexts never bleed                           | Property/concurrency test with parallel transactions                                                          |

The guard test needs an explicit allowlist of global tables (`org.organizations`, all of `ref`). That list is deliberately small and carries a comment saying additions need a decision row — otherwise the guard quietly erodes as someone adds a table and appeases the test.

## Risks

1. **Reference data accuracy.** The 8 divisions and 64 districts are stable and I can state them reliably. The ~495 upazilas/thanas I will not invent: made-up place names in a delivery system produce mis-routed parcels and a zone table nobody can trust. I will seed from a sourced dataset with provenance recorded, and if none is available, seed divisions and districts only, mark thanas as requiring the courier's own area list (which is the authoritative source anyway, M12), and say so in the report rather than padding the table.
2. **Changing M00's compose file.** `POSTGRES_USER` changes, so an existing dev volume keeps the old superuser. The migration path is `docker compose down -v`, which destroys local data — acceptable now, when there is no data, and never acceptable later. The README and the M01 progress entry both say so explicitly.
3. **Testing that something is impossible.** The isolation tests must fail loudly if RLS is silently disabled. Each one asserts a specific error or a specific zero, never a bare truthy — and I will verify the suite catches a deliberately broken policy before declaring it green.
4. **`erp_app` needs enough grants to work and no more.** Too few and every later milestone hits permission errors; too many and the isolation is theatre. Grants are per-table through the helper, and the guard test checks them.
