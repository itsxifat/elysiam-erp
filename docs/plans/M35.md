## Split (2026-10-05)

Built in two parts so the pricing rules exist before checkout (M34) needs them:

- **M35a, offers** (items 1 and 2: flash sales and discounts; decisions D-540 to D-549),
  started on 2026-10-05 beside M31 to M33 on branch `m35a-offers`. Its screens live with the
  promo codes under Campaigns; the Website section links to them.
- **M35b, the rest** (items 3 to 8: landing pages, campaign links, tracking, the ncom.bd
  connector, the packing scanner, order labels; decisions D-550 to D-559), after M33.

## What this is, in plain words

Everything the old admin panel did besides products, orders and customers: time-limited flash
sales, automatic discounts, the landing pages at `/lp/<code>`, the short campaign links
(`?cu=12345`), the Facebook pixel and Google Analytics set-up, the link that lets ncom.bd sell
the brand's products, and the phone app the packers scan parcels with.

## Scope

1. **Flash sales** (M35a; D-542, built 2026-10-05): `promo.flash_sales` and `promo.flash_sale_items` (per SKU: sale
   price, unit limit, units sold), with start, end, banner, slug, priority, "show on home
   page". A sale unit is claimed atomically at checkout (conditional update on the sold count)
   and given back when the order is cancelled or returned. `quoteCart` takes the cheapest live
   offer below the shelf price, then the one ending soonest (the old site's rule).
   Console: **Campaigns → Flash sales** (D-549; the Website section links there) with a product
   picker and per-size prices and limits. Storefront: `GET /storefront/v1/flash-sales` and
   `/:slug`, built by the storefront module (M33/M34) on `PromoApi.storefrontFlashSales` and
   `storefrontFlashSale` (D-548).
2. **Discounts** (M35a; D-540, D-541, built 2026-10-05): the promo module gains what the old site's engine had: automatic
   discounts (no code), buy X get Y, tiered by subtotal, first order only, minimum quantity,
   products or categories, stacking with priority, per-customer and total limits. The pure
   rules (`computeDiscounts`, ported from the old `lib/discounts.js` into integer poisha) live in
   `packages/domain/src/promo/` with fast-check tests; the desk and the website use the same
   function. Console: the promo-code screen becomes **Discounts** with the new kinds.
3. **Landing pages** (M35b; D-550 onward): `storefront.landing_pages` keeps the old site's model (code,
   name, SEO, theme, blocks as JSON, offers, shipping, promotions, form, active, views) with
   one version row per publish. Console: **Website → Landing pages**, the old editor rebuilt
   with the ERP's kit (block list, offer builder, promotions, preview). Storefront:
   `GET /storefront/v1/landing-pages/:code`, and orders through `POST
/storefront/v1/landing-pages/:code/orders`, priced **by the ERP from the page's offer**
   (never from the request), stock held like checkout, channel `landing_page`. This replaces
   the old route that numbered orders by counting and could drive stock negative.
   - This is the website's existing landing pages, not the separate page builder the owner
     removed on 2026-10-02 (D-290, M29).
4. **Custom links** (M35b): `storefront.custom_links` (5-digit code, title, target, highlighted
   products, banner, pop-up, active, views). Console: **Website → Campaign links**.
   Storefront: `GET /storefront/v1/custom-links/:code`.
5. **Tracking** (M35b): the Meta pixel and Conversions API and GA4 settings move to
   **Website → Tracking** (the access token and API secret encrypted). The website posts
   browser events to `POST /storefront/v1/events`; the ERP worker sends them to Meta and GA4
   (ported from the old site's working `lib/tracking/meta.js` and `ga4.js`) and keeps a log
   for the retention the settings name. The server-side Purchase fires from the ERP when a web,
   landing or marketplace order is placed or paid, with the old event ids
   (`purchase_<order>`) so the browser and server events still deduplicate.
6. **ncom.bd connector** (M35b): the ERP implements ncom's "contract 1" at
   `/ncom/v1/*` (ping, products, products/:id, categories, stock, reserve, release) and its
   order intake, webhook and outbox, ported from the old site's `lib/ncom*.js` and checked
   with its `scripts/ncom-check.mjs`. Variant ids: the old site's variant ids keep working
   through `storefront.legacy_ids`; new products use SKU ids. Holds use the inventory
   reservation, keyed by ncom's order reference. Credentials encrypted on **Website →
   Marketplace**. The website's nginx forwards `/api/ncom/*` to the ERP so ncom's settings do
   not change (M37).
7. **Packing scanner** (M35b): `POST /v1/scanner/sign-in` (email and password, or the staff
   member's existing session, returning a 30-day device token), `GET /v1/scanner/shipment?code=`
   (tracking code, order number or consignment id → the packing list). The Android app's API
   base moves to the ERP's admin host; the app is otherwise unchanged. The console gets a
   **Scan** page using the camera, like the old `/admin/scan`.
8. **Order labels** (M35b): the old thermal label sheet (with the merchant id and a QR code)
   on the orders list as a bulk action.

## Acceptance checks

1. A flash sale with 5 units: 20 concurrent checkouts sell exactly 5 at the sale price, the rest
   at shelf price or refused as the sale's rules say; cancelling one gives the unit back.
   (M35a proves it at the claim, where checkout will call it: 20 orders, each line charged the
   sale price, claim at once; exactly 5 hold claims, the rest are refused; a claim must name a
   whole line charged the sale price. Repricing a refused line at the shelf price is M34's.)
2. The ported discount engine gives the old engine's answer on a set of recorded carts
   (fixtures exported from the old site), to the poisha. (M35a runs the old engine itself,
   copied verbatim, beside the port on thousands of generated carts and eleven named cases from
   the old admin's offers: the old site's database is not reachable from the build, D-540.
   M36's export can add recorded carts to the same test.)
3. A landing-page order is priced from the page's offer whatever the request says, and its stock
   is held.
4. `scripts/ncom-check.mjs` from the old site passes against the ERP's connector.
5. The scanner's sign-in and shipment lookup work with a device token; a revoked token is
   refused.
6. `pnpm verify` green; ledger-auditor on the pricing, stock and promo diff.
