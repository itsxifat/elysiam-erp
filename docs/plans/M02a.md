# M02a: Identity, auth and request context

Branch: `m02a-identity-auth` · Effort MAX · Architecture §6, §25 · Depends on M01 (done, merged)

## Scope

Every request knows who the user is, which org they are acting in, and which roles they hold there. Nothing decides what they may _do_ with that — the permission matrix, `serializeFor`, audit and approvals are M02b.

The interesting tension is that M01 made tenant isolation a database property, and identity is the one thing that genuinely spans orgs: one person can work for three of the five brands with a different role in each (§5 exception 4). So `iam` is where the tenancy model has to bend, and the bend has to be exact rather than convenient.

### Out of scope

- The CASL matrix, `serializeFor()`, audit, approvals — M02b.
- Enforcing branch scope on queries. The data model records it; enforcing it is a permissions concern.
- A real SMS provider. Phone OTP goes through a fake (M16 brings the real one, D-012).
- Login and org-switcher **UI** — M05 builds the console shell. M02a ships the API and the org resolution it needs.

## Data model

New schema `iam`. Better Auth owns most of it; its required shape was read from the library rather than guessed.

| Table                     | Tenant?                          | Notes                                                                                                         |
| ------------------------- | -------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `iam.users`               | **global**                       | A person, not an org's property. Carries `is_super_admin` (§6: super_admin is global, not a membership role). |
| `iam.sessions`            | **global**                       | Plus `active_org_id`: the org switcher's choice lives in the session (§6).                                    |
| `iam.accounts`            | **global**                       | Better Auth credential storage.                                                                               |
| `iam.verifications`       | **global**                       | OTP and email verification tokens.                                                                            |
| `iam.two_factors`         | **global**                       | TOTP secret and recovery codes.                                                                               |
| `iam.memberships`         | **tenant, with a second policy** | user × org × role.                                                                                            |
| `iam.membership_branches` | **tenant**                       | Branch scope, as rows rather than a uuid array, so the composite FK from D-047 applies.                       |

**The five global tables are a deliberate exception and will be declared in `GLOBAL_TABLES`.** M01's guard is opt-out precisely so this has to be argued for rather than omitted: a user row genuinely belongs to no org, and putting `org_id` on it would mean a person cannot work for two brands.

**`iam.memberships` gets two permissive policies**, which PostgreSQL ORs:

1. the standard org policy — so "list the users in this org" is isolated automatically, like every other tenant table;
2. a self policy, `user_id = current_setting('app.user_id')` — so the org switcher can answer "which orgs may I enter" without a cross-org read of anyone else's rows.

That is §5 exception 4 expressed as SQL rather than as an application-layer promise. It needs a decision row, and a test that org A cannot see org B's memberships for _other_ users while still seeing its own.

## Behaviour

- **Better Auth** with the `twoFactor` and `phoneNumber` plugins, on the Drizzle adapter, writing into `iam`.
- **2FA is required for `super_admin`, `org_admin`, `accounts` and `investor`** (§6). Enforced server-side on session issue, not merely offered.
- **Sessions**: httpOnly, Secure, SameSite=Lax, scoped to the parent domain so the console works inside the Chatwoot iframe (§16).
- **Rate limits** on login and OTP, per IP _and_ per identifier (§25). Per-identifier matters: per-IP alone is useless against a botnet and punishes shared NAT, which is most of Bangladesh's mobile traffic.
- **CSRF**: Origin check plus a double-submit token on cookie-authenticated mutations.
- **Branded login (D-035)**: the route or hostname resolves an org; unknown hosts fall back to the generic login.
- **Request context**: user, active org, roles, branch scope, request id — the object every later milestone's guard reads.

## Risks

1. **Better Auth owns its schema.** Its migration tooling wants to create tables itself; ours must own them so RLS, grants and the guard apply. I map its models onto Drizzle tables in `iam` and let our migrations create them. If its expectations shift, the failure is a startup error, not a silent one.
2. **The self policy is a cross-org read by design.** It must be scoped to `app.user_id` exactly, or it becomes "any authenticated user reads every membership". This gets an adversarial test in the same style as M01's.
3. **2FA enforcement is a negative.** "Cannot log in without it" passes just as happily if login is broken entirely, so the test asserts the positive path too.
