# M16: Buyer profiles, notifications, basic promo codes (Track A)

Phase 2 · Effort XHIGH · Depends on: M11 · Gate: G5 · Architecture §10

> Planned on 2026-10-01, before the build, under continuous build mode (no approval
> pause; the plan is still written first).

## Scope

Three things a brand does with the buyers it already has:

1. **Know them.** A buyer profile: orders, delivered and returned, lifetime value,
   average order, first and last order, favourite categories and sizes, and an RFM
   segment recomputed nightly.
2. **Talk to them.** A `notify` module: SMS through a provider port with a fake and
   one real adapter, bn and en templates, an opt-out list, quiet hours 21:00–09:00
   Asia/Dhaka for everything but OTPs, and a delivery log.
3. **Reward them.** Promo codes (percent, flat, free delivery) with a minimum order,
   a maximum discount, usage limits in total and per customer, a validity window,
   scope by SKU, category and channel, and personal single-use codes. Validated by a
   pure function, applied in the order desk and at the till, and recorded in a
   redemption ledger. Birthday and anniversary codes are issued by a daily job.

Plus a re-engagement list: buyers with no purchase in N days, filtered, exported.

## Out of scope

- WhatsApp templates (Phase 5) and in-app notifications beyond the log.
- Meta custom audiences from the re-engagement list (Phase 3).
- Promo codes on landing pages (M29).
- Campaign attribution (M18). A code carries an optional campaign id and nothing
  reads it yet.

## Data model

New schemas `promo` and `notify`, and one table in `sales`. All tenant tables with
`org_id`, RLS ENABLE and FORCE, composite tenant foreign keys, minimal grants.

- `promo.codes`: code (unique per org, case-insensitive), kind, value (bps or
  poisha), min order, max discount, total limit, per-customer limit, valid from and
  to (Dhaka dates), channels, personal customer id, campaign id, status.
- `promo.code_scopes`: SKU or category ids a code is limited to.
- `promo.redemptions`: append-only. Code, order or POS sale, customer, discount
  given, and a status that goes `applied` → `released` when an order is cancelled
  before delivery. Unique per (code, order) so a retried order applies once.
- `notify.templates`: key, channel, bn and en bodies with named variables.
- `notify.opt_outs`: phone (normalised) and channel, per org.
- `notify.messages`: the delivery log. Template, channel, recipient phone, rendered
  body, state (`queued`, `deferred`, `sent`, `failed`, `suppressed`), provider
  message id, error, send-after time. The phone is stored because it is the
  address; it is masked in logs and never leaves in an event payload.
- `sales.customer_segments`: customer, RFM scores and segment, computed on.
- `sales.occasion_issues`: customer, occasion, year, code, message. Unique per
  (org, customer, occasion, year): the idempotency the check asks for, in the
  database rather than in the job's memory.
- `sales.orders.promo_code_id` gains its foreign key.

## Domain functions and what tests them

In `packages/domain/src/crm` and `packages/domain/src/promo`:

- `rfm.ts`: recency, frequency and monetary scores (quintiles within the org) and
  the segment names. Table-driven tests (check 1) and a property that every buyer
  gets exactly one segment.
- `occasions.ts`: who is due today in Dhaka, including 29 February in a non-leap
  year (falls on 28 February).
- `promo/validate.ts`: `validatePromo(code, basket, context)` returns a discount or
  a reason. Table-driven tests for expired, not yet valid, limit reached, customer
  limit reached, minimum order not met, wrong channel, out of scope, and personal
  code used by someone else (check 3). Properties: the discount never exceeds the
  basket, the max discount or the eligible lines; free delivery discounts only the
  delivery charge.
- `notify/quiet-hours.ts`: `nextSendTime(now)` returns now outside 21:00–09:00 and
  the next 09:00 inside it; OTPs are never deferred (check 4).

Money: a promo discount is an order discount, so it reaches the books through the
existing delivery posting (Sales discounts), not through a new posting rule. No
new account or rule is needed; if one turns out to be, it gets the §7 row and a
decision row.

## API, jobs and screens

- `GET /v1/customers/:id/profile`: stats, segment, occasions, recent orders.
- `GET /v1/crm/reengagement` and `/export`: gated like the buyer list
  (`export BuyerExport`, D-148), audited, capped.
- `/v1/promo/codes`: list, create, update status. `POST /v1/promo/validate` for the
  desk's live check.
- Orders: the desk sends a code, not an id and not a discount. The server
  validates it inside the order's transaction, sets the discount and records the
  redemption. The client-supplied `promoCodeId` on order create is removed.
- POS: `PROMO_CODES` is bound to the promo module, replacing `NoPromoCodes`.
- `/v1/notify/templates`, `/v1/notify/opt-outs`, `/v1/notify/messages` (the log).
- Jobs: `crm.rfm` nightly; `crm.occasions` daily at 09:00 Dhaka; `notify.send`,
  enqueued in the caller's transaction and scheduled for its send-after time.
- Console: the buyer profile (from the buyer list and order detail), promo codes,
  notification templates and log, the re-engagement list, and a promo field in the
  order desk showing the discount as the server computed it.

## Decisions to record

- **D-012 stays OPEN.** The provider port, a fake, and one adapter built from a
  gateway's official public documentation, off by default and listed under
  unverified integrations. Candidate: BulkSMSBD, whose developer page
  (bulksmsbd.com/bulksms-api-bangladesh.php, read 2026-10-01) documents
  `POST https://bulksmsbd.net/api/smsapi` with `api_key`, `senderid`, `number`
  (`8801XXXXXXXXX`, comma-separated) and `message`, success code `202`, error codes
  `1002`–`1021`, and a balance endpoint. It does **not** document the response
  body's shape or how Bangla text is sent, so the adapter treats anything but a
  recognisable `202` as a failure and the gaps are written into the unverified
  row. If the client already uses another gateway, that one replaces it.
- The RFM quintile method and segment names (ASSUMED).
- A redemption is released when its order is cancelled before shipping, and kept
  once the order ships, returned or not (ASSUMED).
- Occasion codes: which kind and value by default, per org configuration (ASSUMED).

## Risks

- **A discount the client decides.** The desk must never send an amount the
  server trusts; the server derives it from the code, in the same transaction that
  records the redemption.
- **A limit crossed by a race.** Two orders using the last use of a code at once.
  The redemption insert is guarded in the database (a counter with a conditional
  update), not by read-then-write, and a test runs the race against real Postgres.
- **A message sent at 2 a.m.** Quiet hours are applied when the send is scheduled,
  and the send job checks again, so a job delayed past 21:00 defers rather than
  sends.
- **An occasion job that runs twice.** The unique row in `occasion_issues` makes the
  second run a no-op; a test runs the job twice.
- **Personal data.** Phones in the delivery log are the address and stay in the
  tenant table; logs mask them; event payloads carry ids only.
