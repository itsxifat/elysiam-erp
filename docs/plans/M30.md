## Scope

### Part 1 (this build)

1. **Security review with fixes.** A focused review of the surfaces where a mistake costs
   the most: authentication and 2FA, the permission guard and route matrix, tenancy (RLS,
   `withOrg`, the analytics role), the ledger and every money path (wallets, payouts,
   payroll, investors, loans, advances), the public order intake (signatures, Turnstile,
   rate limits), file uploads and signed URLs, the investor portal, CORS and security
   headers, secrets and personal data in logs. Every high-severity finding is fixed with a
   regression test; medium and low ones are recorded as follow-ups. The `ledger-auditor`
   reviews any fix that touches money or tenancy.
2. **k6 load tests** for the order desk APIs and the public intake, measured against §29.
   Run in the official `grafana/k6` image against a locally started built stack (API and
   worker from `apps/server/dist`) on a throwaway database, never on `elysium_dev`.
   Measured p95s and a verdict per target are written to `docs/review/M30/load-test.md`;
   a target that is missed gets a documented plan (check 1 allows that).
3. **Route report** (check 3): `pnpm check:routes` green, plus a generated report listing
   every route with its declared ability, its route-matrix fixture and the test files that
   call it, committed at `docs/review/M30/route-report.md`.
4. **Accessibility pass** over the console's main screens, the till and the portal: the
   axe-in-Playwright pattern the stack specs already use (WCAG 2.1 AA tags), serious and
   critical violations fixed.
5. **Training guides** (plain language, short, one per role: sales agent, accounts,
   warehouse, branch manager, HR, org admin) and a **go-live checklist**, in `docs/`. The
   owner signs the checklist (check 5); the build does not.

## Approach

### Security review

Four read-only reviewers in parallel, one per surface (auth and permissions; tenancy, files
and the investor portal; money paths; the public endpoints and the browser clients), each
reporting findings with severity, file and line, an exploit, a fix and the test it belongs
in. Every finding is checked against the code before it is acted on. High: fixed here,
each with a regression test that fails without the fix. Medium/low: fixed when the fix is
small and local, otherwise listed as follow-ups with an owner. The findings table goes in
this plan's status and in the progress entry.

### Load tests

- `apps/server/src/testing/load-stack.provision.ts`: a throwaway database (the
  `startTestDatabase` harness, as `desk-stack.provision.ts`), seeded at §29's sizes —
  20,000 SKUs (2,000 products × 10, varied names, as the catalog bench), stock on hand,
  5,000 buyers with addresses — plus throwaway users (sales agents, a marketing user who
  issues the intake key).
- `scripts/load-test.mjs`: provisions, starts the built API and worker on their own ports
  with a local Turnstile stub (the real siteverify client over HTTP, answering success),
  signs the users in through the real Better Auth endpoints, issues an intake key through
  `POST /v1/intake/site-keys`, then runs k6 in Docker (`grafana/k6`, reaching the host
  through `host.docker.internal`) and tears everything down. Wrapped in the heavy lock.
- `load/k6/order-desk.js`: constant arrival rate over the desk's calls — customer lookup
  by phone, SKU search, availability, order save, the queue — tagged per call, with
  thresholds at §29's p95s.
- `load/k6/intake.js`: 20 signed orders per second sustained (§29), each with a fresh
  idempotency key, phone and visitor IP, threshold p95 < 500 ms.
- The intake's rate limits are raised for the run (one source IP at 20/s is the load, not
  an attack) and say so in the report. Turnstile's real round trip to Cloudflare is not in
  the local number; the report says how much to expect on top.
- Numbers from a developer laptop sharing its CPU with Postgres, Valkey, the API, the
  worker and k6 are an upper bound on production's server-side latency, not a production
  figure; the report records the machine and commit, as `pnpm bench` does.
- §29's other rows: reports over 12 months (rollups, M24) and console first load (the
  250 KB bundle gate is in `pnpm verify`) are recorded with the evidence that exists, and a
  plan where it does not.

### Route report

`scripts/check-route-matrix.mjs` already boots the application and lists every route.
`pnpm report:routes` reuses that boot and writes the markdown report: method, path,
declaration (ability, `authenticated` or `public:<reason>`), the fixture file that drives
it in the route-matrix suite, and the test files whose request paths match it.

### Accessibility

A new real-stack spec, `apps/console/e2e/a11y.stack.ts`, visits the console's main
screens as the roles that use them, in both themes, and runs axe with the WCAG 2.0/2.1 A
and AA tags; serious and critical violations fail it. The till runs its own offline
Playwright run (`apps/pos/e2e`) and the portal its `investor.stack.ts`, which already
asserts axe on its screens; the till gains the same assertion on its main screens.

## Risks

- **A fix that breaks a flow.** Every fix ships with its regression test and the full
  `pnpm verify`; money and tenancy fixes also get the ledger-auditor.
- **Load on a shared machine.** The k6 run holds the heavy lock, uses its own database and
  ports, and stops every child process tree at the end, as the stack specs do.
- **Overlap with M14b.** Logger, Sentry, health and Pages headers stay M14b's; anything
  found there is handed over in the report.
- **Numbers that flatter.** The report states what the local run leaves out (Turnstile's
  round trip, the network to Singapore) instead of letting the figure stand alone.
