## Scope

A showroom sells at a till that keeps working with no internet. Every sale
reaches the books exactly once when the connection returns, and nothing the till
sends can push stock negative or post a discount nobody authorised. Each branch
has a dashboard and closes its day against a counted drawer.

## Out of scope

- Promo code validation. The till calls a `PROMO_CODES` port that answers "no
  code is valid" until M16 binds it.
- Card terminal integration. A card tender is a recorded amount into a wallet.
- Customer display, loyalty points and gift cards.
- Hardware drivers. Receipts print through the browser and print CSS.

## Data model

Schema `pos`, migrations 0068 to 0070.

- `registers`: a till, its stock location, and one wallet per tender.
- `shifts`: opened with a float, closed against a count.
- `sales`, `sale_lines`, `sale_tenders`.
- `returns`, `return_lines`, `return_tenders`.
- `review_items`: a held document waiting for a person.
- `branch_closings`, `branch_closing_wallets`: the day close, one M08 closing
  per wallet.

Two shapes to know:

- **The till's documents keep the till's ids.** `sales.id`, `returns.id`,
  `shifts.id` and `branch_closings.id` have no default. The till generates them
  offline, so a re-sync lands on the same row, the same movements and the same
  journal key.
- **No till balance is stored.** Cash is derived from ledger lines, as in M08.

0070 holds the triggers: a register sells from its own branch's location into
its own branch's hand cash, a posted document is immutable, and `erp_app` holds
no DELETE on any `pos` table.

## Domain functions and what tests them

In `packages/domain/src/pos`, tested in `pos.test.ts`:

- `cart.ts`: `priceLines`, `settleTenders`. The server recomputes every total.
- `discount-policy.ts`: a discount ceiling per role, per branch, never merged
  across roles (D-075).
- `holds.ts`: `saleHoldReasons`. Why a sale is held instead of posted.
- `returns.ts`, `shift.ts`: refund limits and the expected drawer.
- `canonical.ts`: canonical JSON for the payload hash.

Posting rules `pos-sale.ts` and `pos-return.ts`, tested in
`pos-posting.test.ts`.

## API and screens

- 18 routes under `/v1/pos`: registers, session, price list, promo check,
  shifts, sync, receipts, sales, reviews, branches, summary, closings.
- `POST /v1/pos/sync` takes the till's queue. Each document gets its own
  transaction, so one bad document cannot roll back the ones behind it.
- The `pos` PWA: setup, sell, queue, returns, an 80 mm receipt, a service
  worker and an IndexedDB store.
- Console: `/branches` and `/branches/$branchId`.

## Decisions to record

Rows D-161 to D-167 in `docs/decisions.md`.

- D-161: POS routes reuse existing subjects. Moving till money is
  `update Wallet`, reading is `read Wallet`, the price list is `read Catalog`,
  dashboards are `read LedgerReport`. **OPEN for the client:** today only org
  admin, accounts and a branch manager can operate a till. Showroom sales staff
  cannot.
- D-162: Discount ceilings of 100% for org admin, 20% for branch manager and 5%
  for sales. ASSUMED.
- D-163: A document is identified by the till's UUID plus a payload hash. A
  different payload under a used id is refused as a conflict.
- D-164: A sale that cannot post is held as a review item, never refused. The
  person who rang it up cannot resolve it.
- D-165: Tenders are cash, bKash and card. Change is given from cash only.
- D-166: The branch day close reuses M08's closing per wallet, including its
  variance approval.
- D-167: The till restates two money operations locally, proved equal to the
  domain's by test, because the server recomputes everything.

## Risks

- **Double posting on re-sync.** The first delivery inserts with
  `on conflict do nothing`. The journal key derives from the same id.
- **Negative stock from an offline sale.** The shelf is only known by trying.
  A shortfall becomes a review item and stock stays at zero.
- **A stale offline price.** A price other than the catalog's is a hold reason,
  and a lower price counts as discount.
- **Ports bound to a refusing default in production.** The module ships with
  defaults that refuse. If integration forgets a binding the till fails loudly
  rather than quietly, but it does fail. The route-matrix suite must drive the
  real bindings.
