# M04: Platform services

Phase 0 · Effort XHIGH · Depends on: M02b · Architecture §3, §19, §20, §22, §23

## Scope, in my own words

The plumbing every later module reuses. Nothing here is a feature the client
would name, and everything here is something six later milestones would
otherwise each invent differently: jobs, events, realtime, files, PDFs, the
typed client.

Two of these are load-bearing for "keep track of all money":

- **The outbox.** M03 posts journals inside a transaction. Everything that must
  happen _because_ a journal posted — a courier booking, an SMS, a dashboard
  refresh — must not happen if that transaction rolls back, and must happen
  exactly once if it commits. Invariant 6 says no external call inside a
  transaction; `enqueue(tx, …)` is how that rule becomes possible to follow
  rather than merely stated. Until now `ApprovalsService` has held its events in
  an in-memory array, which `.claude/rules` explicitly forbids ("realtime events
  go only through the outbox") and which the acceptance audit flagged.
- **Idempotency.** §23 requires `Idempotency-Key` on mutations. M03's
  `ledger.post()` already keys on content, and the security review found the
  matching trap: a job that rebuilds its draft and retries after a Dhaka
  midnight gets `IDEMPOTENCY_CONFLICT` instead of its journal back (L5). M04
  owns job retries, so M04 is where that has to be settled.

## Slices, in build order

Each slice ends green and committed.

### 1. Events and jobs

- `packages/contracts/src/events.ts` — a Zod schema per §19 catalog entry, and
  the room list each one goes to. The rooms belong next to the payload because
  §19's rule is that the _server_ decides rooms; putting them in the contract
  means a subscriber cannot widen its own audience.
- `events.outbox`: `id, org_id, name, payload, rooms, created_at, dispatched_at,
attempts, last_error`. Tenant table, RLS, append-then-mark rather than delete
  so a dispatch can be audited.
- `enqueue(tx, queue, payload, opts)` — writes a pg-boss job **through the same
  transaction**, so the rollback story is the database's rather than ours.
- The dispatcher: claims undispatched rows with `for update skip locked`, hands
  them to in-process subscribers and the realtime bridge, marks them dispatched.
- Replace `ApprovalsService.emitted` with real outbox writes, keeping the
  existing tests' ability to observe what fired.
- Dead-letter → `job.failed`, per §20.

Acceptance checks 1 and 2 land here.

### 2. Realtime gateway `/rt`

Socket.IO with the Valkey adapter, cookie authentication reusing the same
session resolution the HTTP surface uses, and **server-assigned rooms** from the
caller's memberships. A client asking to join a room is refused, not ignored —
§19's rule only means something if trying is an error. Check 3.

### 3. Files and PDFs

Storage driver interface with `local` and `r2`; presigned PUT with size and MIME
limits; `files.objects` rows carrying sha256, owner and visibility; a private
download that authorizes _before_ signing. The image job re-encodes with sharp
and strips EXIF — a customer photo carrying GPS is invariant 10's problem, not
just a size problem. Gotenberg for PDFs with Bangla fonts embedded. Checks 4
and 5.

### 4. API layer

OpenAPI from the contracts, `packages/api-client` generated with a drift check
in `pnpm verify`, problem+json for every error, `Idempotency-Key` middleware,
and the rate limiter moved from memory to Valkey (D-056's stated exit). Check 6.

### 5. i18n and feature flags

bn/en scaffolding with a missing-key checker, Asia/Dhaka date helpers already in
`packages/domain/src/dates`, and `org.feature_flags` with a helper (D-031).

## What I expect to be hard

- **Exactly once.** pg-boss gives at-least-once. The honest position is that
  every job must be idempotent (§20 says so) and that the outbox dispatcher must
  not lose a row if it dies mid-flight. `for update skip locked` plus a
  dispatched marker gets that; a delete-on-dispatch would not.
- **Realtime payload discipline.** §19 says payloads carry ids plus only fields
  every recipient role may see — never cost, never a full address. That is
  `serializeFor`'s problem restated for a channel it does not currently cover,
  and the emit helper has to enforce it rather than trust callers.

## Assumptions to record

- **D-09x**: the outbox is polled rather than `LISTEN/NOTIFY`-driven, because a
  missed notification is silent and a poll is not. Interval configurable.
- **D-09x**: `Idempotency-Key` responses are stored for 24 hours per user and
  route (§23), in Postgres rather than Valkey, because a replayed response that
  disagrees with the database is worse than a slow one.
