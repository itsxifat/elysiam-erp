## Scope

Three things HR does with the order desk's work:

1. **Set targets.** A monthly target per employee or per team on one metric
   (`confirmed_orders`, `delivered_orders`, `delivered_revenue`), split into weeks by the
   working days in each week with largest remainder, so the weeks always sum to the month.
   Progress comes from a rollup of the orders each agent confirmed and delivered, and
   `target.progress` tells the employee and HR when it moves.
2. **Pay for them.** Bonus rules as versioned JSON, evaluated by a pure function, previewed
   against a month's targets, approved by a second person, and applied to a draft payroll
   run as bonus inputs that the run's own maker-checker approval then covers.
3. **Measure the desk.** Pickup time (median and p90) and orders handled per active hour,
   computed from the outbox's order events, with reassignment resetting the clock for the
   new assignee.

Plus an agent dashboard (my targets, my weekly progress, my pickup time) and HR reports
(every target's progress, every agent's productivity) in the console.

## Out of scope

- The cross-org leaderboard and `analytics.daily_agent` (M24). M20's rollup is HR's own.
- Real active time from an activity extension. M28 is removed from scope (D-292), so an
  active hour is, for good, an Asia/Dhaka clock hour with at least one desk action (D-276).
- Team bonuses: a team target tracks progress but pays nothing until the client says how a
  team bonus is shared (D-273).
- Targets on metrics other than §12's three.

## Data model

All in schema `hr` (§3 gives hr "targets, bonus rules"), tenant tables with `org_id`, RLS
ENABLE and FORCE, composite tenant foreign keys, minimal grants. Migrations
`0081_m20_targets_schema` (generated), `0082_m20_targets_policies` and
`0083_m20_targets_integrity` (custom); 0080 is the fraud removal.

- `targets`: month (`YYYY-MM`), metric, scope (`employee` | `team`), the employee or the
  team name, the branch (for branch-scoped readers), the calendar the split used, target
  value (orders or poisha), achieved, progress time, status (`active` | `cancelled`).
  One active employee target per (org, month, metric, employee).
- `target_members`: the employees a target counts (one for an employee target).
- `target_weeks`: week number, first and last day, working days, planned, achieved. The
  planned column never changes after insert.
- `bonus_rules` and `bonus_rule_versions`: a named rule on one metric; each edit is a new
  version whose definition never changes; status `draft → pending_approval → approved`
  (or `rejected`), an approved version supersedes the previous one. One approved and one
  pending version per rule, by partial unique indexes.
- `bonus_awards`: what a rule version paid one employee for one target in one payroll run,
  linked to the `payroll_inputs` row it created. Insert and delete only while the run is a
  draft (trigger).
- `desk_events`: the productivity facts, one row per outbox event id (unique), written by
  the worker's subscriber: order, kind (`created`, `assigned`, `claimed`, `confirmed`,
  `cancelled`), assignee, actor, time. Append-only.
- `events.outbox.actor_user_id`: who acted, from `app.user_id` at emit time (D-277).

## Domain functions and what tests them

In `packages/domain/src/targets` (exported as `@elysium/domain/targets`):

- `weeks.ts`: `monthWeeks(month)` (Saturday-start weeks clipped to the month) and
  `splitTarget(total, month, calendar)` by working days with largest remainder. Property
  tests (check 1): the weeks sum exactly, every part is non-negative, parts differ from
  their exact share by less than one, the weeks tile the month; table tests for Eid
  holidays, a zero-working-day month and a one-unit target.
- `progress.ts`: `rollupProgress(weeks, members, metric, dailyResults)`, achieved per week
  and in total, percentage in basis points (no floats).
- `bonus.ts`: `parseBonusRule(json)` (structure and meaning: thresholds ascending, tier kind
  fits the metric) and `evaluateBonus(rule, { target, achieved })`. Table-driven tests
  (check 2): below the first tier, exactly at a threshold, cumulative tiers, per unit
  above target, basis points of excess revenue, the cap, zero target refused.
- `productivity.ts`: `pickupSamples(events)` and `productivity(events, window)`; median and
  p90 by nearest rank. Seeded event streams (check 3): queue then claim, assigned at
  creation then confirmed, reassignment before pickup, reassignment after pickup, an
  action by someone else, a self-created order, duplicate and out-of-order events.

Money: a bonus is an ordinary payroll bonus input, so it reaches the books through M19's
payroll posting (Dr Bonus expense). No new posting rule.

## API, jobs and screens

`PerformanceModule` in `modules/hr` (D-270), every route under `/v1/hr`, subject `Target`
(D-278):

- `GET /targets`, `GET /targets/:id`, `POST /targets`, `POST /targets/:id/cancel`,
  `POST /targets/refresh`.
- `GET /bonus-rules`, `POST /bonus-rules`, `POST /bonus-rules/:id/versions`,
  `GET /bonus-rules/versions/:versionId/preview?month=`,
  `POST /bonus-rules/versions/:versionId/submit` (raises `bonus_rule`; the executor
  approves only the version that names the request).
- `GET /payroll/runs/:id/bonuses` (`read Payroll`), `POST /payroll/runs/:id/bonuses`
  (`create Payroll`): evaluate the approved versions against the run's month and replace
  the run's rule-made bonus inputs.
- `GET /performance/me?month=`: the caller's own targets, weeks and productivity.
- `GET /productivity?from=&to=`: one row per employee with a login, scoped through the
  employee rows (own, branch, org), so an agent gets exactly one row: their own.
- `OrdersApi.agentResults(tx, orgId, range)`: per agent per day, confirmed orders, delivered
  orders and delivered net revenue (through `computePartialDelivery`, as the ledger does).
- Event `target.progress` (§19): `user:{each member}`, `org:role:hr`; target id, achieved,
  pct.
- Worker: an outbox subscriber on `order.created`, `order.assigned`, `order.claimed` and
  `order.status_changed` writes `desk_events` and, for a status change that can move a
  target, enqueues `hr.refresh_target_progress` keyed by org and ten-second bucket and
  started after the bucket closes (D-279).
- Console: `/performance` (my dashboard), `/performance/targets`, `/performance/bonus-rules`,
  `/performance/productivity`, and a Bonuses panel on the payroll run.

## Risks

- **A bonus approved twice into payroll.** Awards are unique per (run, target, rule
  version) and replaced, never added, while the run is a draft; a trigger refuses awards on
  a submitted run.
- **A hand-raised `bonus_rule` request activating a rule.** The executor activates only a
  version whose `approval_request_id` is that request.
- **An agent reading another agent's numbers.** Every read is scoped through
  `scopeWhere`/`assertInScope`; check 4 runs the API as two agents.
- **Double-counted events.** `desk_events` is unique on the outbox event id; the subscriber
  is at-least-once and idempotent.
- **A flood of progress events.** One recompute per org per ten-second bucket (D-279), and an
  event only when a target's achieved figure changed.
