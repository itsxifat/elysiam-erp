## What was already there

- The count (`packing.order_lots`, D-805): one lot with no row, set by the label desk or the packer,
  with no rule for who decides first.
- A change already sent the order back: labels printed at another count do not count (D-805), so
  Ready for label listed it again. Nobody was told, and nothing marked it.
- At the table the old label still worked. It closed the lot and started the next one, and the
  packer heard about the missing labels only at the very last scan, after filling every bag.

## Scope

1. **The first answer** (D-941). Every order starts as one lot. The brand's limit
   (`packing.settings.lot_ask_above_pieces`, Packaging → Packing → Settings; empty asks nobody): an
   order with more pieces than that is asked how many lots when a person confirms it.
2. **The last word** (D-942). The packer's Lots button sends the revised count. The order goes to
   the top of Ready for label, marked with the old and new count, who and when. Every lot's label
   prints again, because each says "Lot n of N". The table waits and is told when they are out.
3. **A count that can be packed** (D-943, D-944). Never more lots than the pieces can fill, whoever
   sets it, and fixed once the order is packed.
4. **Only the new labels work** (D-945). After a revision a whole-order code is refused on an order
   in several lots, a sticker thrown away does not come back, and pages queued for the old count
   are cancelled.

## Out of scope

- A bag split at the dispatch table, after packing (refused since D-944). It needs its own label
  path if the owner wants it.
- Asking on a Replace: a replacement starts as one lot. Carrying the old count over is a follow-up.
- Telling the courier the lot count (D-809, none documents one).
- Asking again when an edit changes the pieces of a confirmed order. The packer's revision covers
  it, except an edit after lots were closed (D-943), which predates M52 and is a follow-up.

## Data model

- `packing.settings.lot_ask_above_pieces` integer, null, check 1 to 500 (migration 0167). The table's
  row security and grants already cover it.
- Nothing else: whether an order was revised is derived from `print_jobs` (its last label printed
  at a count other than today's), so changing the count back unmarks it and its labels count again.

## Domain

`packages/domain/src/packing/lots.ts`: `judgeConfirmLots`, `lotCountLimit`, and `judgeLotCount` gains
the pieces and those sealed in closed lots (`more_than_pieces`) and loses `packed` (D-944).
`recording.ts`: `judgePackLabelScan` gains `whole_order`. Property tests in `lots.test.ts`.

## API

- `POST /v1/orders/:id/confirm` takes optional `lots` (1 to 20). `ORDER_LOTS_REQUIRED` (409) asks;
  `LOT_COUNT_INVALID` (400) refuses an answer that could not be packed. Only this route asks, and
  bulk confirm through it; a replacement does not.
- `HandoverGuard.settleLots` is how orders reaches packing (invariant 12): in the confirm's
  transaction, after the order's lock, so the answer rolls back with a refused confirm.
- `GET`/`PUT /v1/packing/settings` carry `lotAskAbovePieces` (absent keeps, null clears).
- `GET /v1/labels/ready` gains `revised { fromLots, by, at }`, those orders first.
- The station's view gains `labelsAwaited`; a label scan and Close lot wait for it to empty.

## Screens

- **Confirm** on the order page and the order desk: `ConfirmLotsDialog`, starting at 1, so the usual
  answer is one key. Not now on the desk leaves the order saved as pending with the reason shown.
- **Packaging → Packing → Settings**: the limit.
- **The packing station**: the Lots dialog says what a change does; a waiting banner; Finish and Close
  lot disabled; a check every five seconds, with a sound and a line when the labels are out.
- **Labels → Ready for label**: a line saying how many changed, each marked "New labels 1 → 2 lots",
  who and when; refreshed every 15 seconds rather than 30.

## Assumptions

- The question is at Confirm, not at order-taking: every channel passes Confirm, a website order has
  no order taker until someone confirms it, and Confirm is when an order becomes ready for its label.
- The limit is off until a supervisor enters a number, so nobody is surprised mid-shift by a deploy.

## Risks

- A label's code does not carry the count, so an old "Lot 1 of 2" scans the same as the new "Lot 1 of
  3" once printed. Only the words on the screens stop the old sticker staying on a bag.
- A session open at the deploy whose labels were never printed now waits at its label scan, where
  it would have been refused at Finish anyway (D-928).
- A two-lot order being packed at the deploy with a whole-order code now needs each lot's own
  label (D-945). Those labels print with every lot since D-912.
- A sales agent can revise their own order through the API, which halts the table (audited). The
  owner may want this limited to the hub.

## Follow-ups

- Carry the old count over to a replacement (the audit's W5).
- Refuse an edit that leaves fewer pieces than the closed lots need (W4; predates M52).
- A browser test of the order desk's question: the order page's is tested, the desk's is not.
