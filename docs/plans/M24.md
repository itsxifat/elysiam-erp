# M24: Analytics, dashboards, leaderboard

Phase 4 · Effort XHIGH · Depends on: M12, M18, M20, M23 · Architecture §18, §19, §5 (exception 2)

> Planned on 2026-10-02, before the build, under continuous build mode (no approval
> pause; the plan is still written first). The owner asked for it fast and lean: what the
> acceptance checks need, solidly tested, nothing extra. Fraud, Chatwoot, landing pages and
> the activity extension are out of scope (D-290 to D-292), so no fraud metric, no response
> time and no landing-page or extension data appear anywhere here.

## Scope

1. **Rollups.** Five daily tables in a new `analytics` schema (§18): `daily_org`,
   `daily_branch`, `daily_channel`, `daily_campaign`, `daily_agent`. One job,
   `analytics.rollup`, rebuilds an org's days from the owning modules' `*.api.ts` —
   delete and insert in one `withOrg` transaction, so a rerun is a no-op and a moved
   attribution moves its row. It runs on order events (one per org per ten-second bucket,
   as D-279), nightly for the last seven days, and on request for a backfill.
2. **The org dashboard** (org admin, own org, `withOrg`): orders placed, confirmed,
   delivered, returned; delivered revenue and gross profit (cost roles); AOV, return rate,
   delivery success; spend, CPO, CPDO, ROAS; cash position and stock value (cost roles);
   a daily series; by channel, branch and campaign; top SKUs; agent performance.
3. **The consolidated dashboard** (platform super admin): every brand's totals and the
   group total from `analytics.daily_org`, read through `withAnalytics()` only.
4. **The leaderboard** (org admins of every brand, super admin): §18's normalized metrics
   per brand for a month, a rank per metric and a composite score with configurable
   weights. D-023: an org admin sees other brands' normalized metrics and ranks, never
   their raw revenue, spend, orders or profit. Read through `withAnalytics()` only.
5. **Insight rules** as pure functions in `packages/domain/src/analytics/insights.ts`.
6. **The LLM narrative**, behind the per-org flag `analytics.llm_narrative` (off): a
   PII-free payload builder, a provider port with a fake, cached per org per Dhaka day. No
   real provider adapter (decision row).
7. **Exports**: the org's daily rollup as CSV or XLSX.
8. **Console** `/analytics`: Dashboard (with insights and the narrative card when on),
   Leaderboard, Group (super admin).

## Out of scope

- Realtime `leaderboard.updated`: the board is computed on read from the rollups, so there
  is no snapshot to announce (D-324).
- Response time (§18): it was the Message Hub's figure, removed with Chatwoot (D-290).
- A screen for leaderboard weights: they are configuration (D-323).
- A real LLM provider adapter (D-327).

## Data model

Schema `analytics`, owned by the new `analytics` module. Every table is a tenant table:
`org_id`, RLS ENABLE and FORCE through `tenantTableSql()`, composite tenant keys where a
table points at another (none needed: ids are copied, not referenced, because a rollup must
survive a campaign or a branch it names being archived). `erp_app` gets SELECT, INSERT,
UPDATE, DELETE (a rollup is a cache that is replaced). The five `daily_*` tables pass
`analyticsReadsAllOrgs` and join `ANALYTICS_READABLE` (D-049's opt-in); `narratives` does
not.

- Order metrics (one column set in `daily_org`, `daily_branch`, `daily_channel`):
  `orders_placed`, `orders_confirmed`, `orders_delivered`, `orders_returned`,
  `orders_cancelled` (cancelled after confirmation), `delivered_revenue_poisha`,
  `gross_profit_poisha`, `delivered_outside_dhaka`, `returned_outside_dhaka`.
- `daily_org` (org, business date): order metrics + `spend_poisha`, `pickup_count`,
  `pickup_seconds`, `computed_at`.
- `daily_branch` (org, date, branch id): order metrics, orders with a branch only.
- `daily_channel` (org, date, channel): order metrics.
- `daily_campaign` (org, date, campaign id or null = unattributed): spend, confirmed,
  delivered, returned, delivered revenue, placed revenue — M18's inputs, attribution read
  at rollup time through M18's own resolver.
- `daily_agent` (org, date, user id): confirmed, delivered and delivered revenue for the
  confirming agent (D-272), pickups and pickup seconds (D-276).
- `narratives` (org, generated on, month): the text, the provider, a hash of the payload.

## Domain functions and what tests them

`packages/domain/src/analytics` (`@elysium/domain/analytics`):

- `rollup.ts`: `rollupOrders(facts, days)` — per day, the org row and the rows by branch
  and by channel. Table tests and a property: org totals equal the sum of the channel rows.
- `kpis.ts`: AOV, return rate, delivery success, CPO, CPDO, ROAS, mean pickup from summed
  inputs; null when the denominator is zero.
- `leaderboard.ts`: `normalizedMetrics(current, previous)`, `rankBoard(entries, weights)`
  (competition ranking, rank-based scores, weighted composite), `parseWeights`, and
  `leaderboardView(board, viewer)` — D-023 as a function. Table tests plus properties.
- `insights.ts`: the rules (check 3), each with a fire, a no-fire, a too-small-sample and
  a boundary case.
- `narrative.ts`: `buildNarrativePayload(input)` — an allow-list of numbers, dates and
  codes (check 4).

## API, jobs and screens

`AnalyticsModule`, every route under `/v1/analytics`:

- `GET /dashboard?from&to` — `read Dashboard` (new subject, D-325), own org.
- `GET /insights?month` — `read Dashboard`; the group medians come through `erp_analytics`.
- `GET /narrative?month` — `read Dashboard`; `{ enabled: false }` with the flag off.
- `POST /rollups/refresh` `{ from, to }` (≤ 92 days) — `update Dashboard`, synchronous.
- `GET /export?from&to&format` — `read Dashboard`; gross profit only for cost roles.
- `GET /consolidated?from&to` — `read Dashboard` and a platform super admin.
- `GET /leaderboard?month` — `read Leaderboard`.

Sources, each through its owner's interface (invariant 12): `OrdersApi.analyticsFacts`
(new), `OrdersApi.agentResults` (M20), `OrdersApi.topSkus` (new), `MarketingApi.campaignDays`
(new `marketing.api.ts`), `HrApi.pickupSamples` and `HrApi.employeesForUsers` (new),
`LedgerApi.balancesAsOf` (cash), `InventoryApi.valuation` (stock value). The analytics
repository names only `analytics.*` and `org.*`.

Jobs: `analytics.rollup` (org, exclusive, keyed by org and bucket or by the nightly date);
`analytics.schedule_rollup` (global, 03:00 Dhaka) fans out the last seven days per brand;
the worker's outbox subscriber on `order.created` and `order.status_changed` enqueues the
event's day.

## Risks

- **A cross-org read that is not the analytics role.** Leaderboard, insights' medians and
  the consolidated view are the only cross-org reads, all inside `withAnalytics()` in the
  analytics module; the role reads `analytics.daily_*` and nothing new. A guard test lists
  what it can read.
- **Raw figures reaching another brand's admin.** `leaderboardView` builds the other
  brands' rows from an allow-list, and the HTTP test inspects the JSON (check 2).
- **A rollup that disagrees with its sources.** Check 1 compares every table with direct
  SQL over seeded orders, spend, desk events and lines, then reruns the job and compares
  again.
- **PII in a prompt.** The payload is built from an allow-list of numeric fields and
  codes; a test plants names, phones and free text in every input and asserts none
  survives (check 4).
- **Cost to a non-cost role.** Gross profit and stock value are named `grossProfitPoisha`
  and `stockValuePoisha`, already in `COST_FIELDS`; the export strips the column itself.
