# M02b: Permissions, audit and approvals

Phase 0 · Effort MAX · Depends on: M02a · Architecture §6, §25

## Scope

Three controls that everything after this milestone leans on:

1. **Permissions.** One declarative CASL matrix, a guard that reads it, and
   `serializeFor()` so a field a role may not read cannot leave the process.
2. **Audit.** Every mutation writes who did what to which entity, before and
   after, with sensitive fields redacted.
3. **Approvals.** Money-moving actions need a second person, and the
   requester ≠ approver rule is enforced by the database rather than by a
   service anyone can forget to call.

Plus the gate that keeps the first one honest: `check-route-matrix` fails the
build when a route ships without a declared ability.

### Out of scope

- Real money-moving actions. M03+ own those; M02b gives them the machinery and
  a demo resource to prove it against.
- The approvals UI. The API and events land here; the inbox is M05.
- Encryption of national ID / payout / KYC fields (§25). Those columns do not
  exist yet; M14a and M20 add them with the encryption.

## Data model

New schemas, both tenant-scoped with the standard isolation block:

- `audit.audit_log` — append-only (INSERT + SELECT grants only). `org_id`,
  `actor_user_id`, `action`, `entity_type`, `entity_id`, `before`, `after`,
  `ip`, `user_agent`, `request_id`, `created_at`. Partitioned by month from the
  start, because this is the table that grows without bound.
- `approvals.approval_requests` — `org_id`, `type`, `requested_by`,
  `amount_poisha`, `payload`, `status`, `decided_by`, `decided_at`, `reason`.
  A **check constraint** `decided_by <> requested_by`, so self-approval fails
  at the database.
- `approvals.approval_thresholds` — `org_id`, `type`, `threshold_poisha`.
- `demo.costed_items` — the demo resource carrying `unit_cost_poisha`, so the
  matrix suite has something real to exercise. Deleted when M06 gives the
  matrix a genuine costed resource.

## Domain

`packages/contracts/src/permissions/` holds the matrix as data: subjects,
actions, scope qualifiers (`own` / `branch` / `org`), and the two protected
field lists (`COST_FIELDS`, `RESELLER_VISIBLE_FIELDS`). `packages/domain` gets
the pure parts: `requiresApproval(type, amount, thresholds)` and the redaction
function, both property-tested.

## API

- `@RequireAbility(action, subject)` decorator + a global guard.
- `serializeFor(ability, subject, data)` applied in an interceptor, so a route
  cannot forget it.
- `POST /v1/approvals` (request), `POST /v1/approvals/:id/decide`.
- Events `approval.requested` and `approval.decided` (§27's table).

## Risks

1. **A guard that defaults to allow is worse than no guard.** The route-matrix
   gate exists precisely because "every route declares its ability" is not
   enforceable by review. It must fail on an undeclared route, and check 6 is
   the demonstration that it does.
2. **`serializeFor` has to run on every path out.** An interceptor catches the
   controller return; it does not catch a stream, a file download or an event
   payload. Those get their own assertions.
3. **Audit must not be bypassable.** An interceptor is the mechanism, but a
   service that writes outside a request has no interceptor — the audit write
   belongs in the same transaction as the mutation, which means a helper rather
   than only a hook.
